# WU-056: A pull request Plumbix merged is closed, never reopened as a change

**Status**: ✅ Complete (2026-11-04) · **Features**: F-010 · **Estimate**: short · **Kai**: FBYPNW (workstream F8QK66, milestone M2 PZTRDV) · **Follows**: WU-065 · **Source**: found on 2026-10-28 with the first real gated pull request (eduard-alloy/plumbix#1)

## Goal

With `merger: plumbix` on a pull-request repository, Plumbix pushes the validated tree itself. GitHub matches a merge commit or a rebase to the pull request and shows it merged, but never a squash, so pull request #1 stayed open after its merge and the next poll opened a second change for the same head (`ChangeByPullRequest` answers open changes only). The task offered two ways out: Plumbix closes the pull request, or the manual refuses the combination. The first acceptance criterion asks for the pull request to be closed without a person, so Plumbix closes it.

## Design

- **At merge time** (`Engine.Merge` → `Landing.PullRequestLanded`, implemented by `pullrequest.Lander`): once the merge record is written and the holding ref removed, Plumbix closes the pull request unless GitHub already shows it merged or closed (a merge commit or a rebase GitHub matched on its own), then comments on it naming the commit that landed, the target, the strategy, the change and the run. The close comes first so the sync's retries never repeat the comment; the cost is that a comment failing after a successful close is lost, which `closePullRequest` logs as that ("pull request closed, but the comment naming the merge was lost") and does not report as an error, since a closed pull request is not visited again and the engine's and the sync's own warnings speak of a pull request still open. Both calls go out as the App (`GitHub.CommentOnPullRequest`, `GitHub.ClosePullRequest`). A failure is logged, never an error of the merge: the merge stands.
- **At sync time** (`Syncer.Apply`): an open pull request with no open change is looked up by `Store.LastChangeByPullRequest`; when its newest change is one Plumbix merged (merged, with a merge record and no GitHub merger), no second change is opened. The pull request is closed again, silently when its head is the validated one, with a comment when commits arrived since, saying they are not part of the merge and need a new pull request. A failed close is logged and retried on the next sync, so a close that failed at merge time heals itself.
- **Not in this unit**: deleting the source branch; refusing `merger: plumbix` with pull requests (the shape works now); Azure DevOps pull requests.

## Steps

1. Store: `LastChangeByPullRequest` with its test.
2. Host: `GitHub.CommentOnPullRequest` and `GitHub.ClosePullRequest` on the REST helper; the `pullrequest.API` interface and its test fake take both.
3. Lander: `PullRequestLanded` and the shared `closePullRequest` (read, close unless already merged or closed, then comment), with its test.
4. Engine: `Landing.PullRequestLanded` on the interface, called by `Merge` once the change reads merged; the fake landing records it, with a test that closes the change from inside the call as a webhook delivery would.
5. Syncer: `landedByPlumbix` and `closeLanded` on the open-pull-request path of `Apply`, with the sync-after-merge test.
6. Docs: README (merger paragraph, App permission), ARCHITECTURE 5.5, CONSTRAINTS, PROJECT, CONTEXT_LOG; `make check`.

## Fixes

**Iteration 1** (`approved`; three findings taken, one advisory finding a real ordering bug): the pull request was closed while the change still read `approved`, so a `closed` delivery arriving in that window would have found the open change and closed it, leaving a merged record on a closed change that `landedByPlumbix` would no longer recognise. The close now runs last, after the change reads merged; the engine test closes the change from inside the landing call and expects `invalid_state`. `landedByPlumbix` also excludes strategy `github`, so the test says what it means. ARCHITECTURE item 8 no longer counts "four steps"; this file's table matches the change's four criteria and carries the step list. Left as documented: an App installed before this unit with `merger: plumbix` needs pull requests write, and until it has it both closes fail and are logged on every sync (README names the permission).

**Iteration 3** (`needs_human` over the App permission risk; the one minor finding taken): `closePullRequest` now closes first and comments after, so a close the sync keeps retrying does not repeat the comment; the sync test counts comments across the retries. Iteration 2 was the poller's own start on the same head, superseded.

**Iteration 4** (`approved`; two doc notes taken): the Design bullet and step 3 describe the close-then-comment order; the lost-comment trade-off is stated in the Design bullet.

**Iteration 5** (`approved`; the one finding, raised by both reviewers, taken): a comment lost after a successful close was reported as a failed close by the engine and the sync. `closePullRequest` now logs that case itself and returns nil, so an error means exactly "still open, try again"; the `Lander` carries the server's logger; the lander test covers the lost comment.
