# WU-046: Import source interface and the Azure importer core

**Status**: ✅ Complete (2026-10-19) · **Features**: F-014 · **Estimate**: one session · **Kai**: Y5EQ0E (workstream TCVR9R, milestone I1) · **Decisions**: A36, A37

## Goal

Read a repository's Azure Pipelines files and turn each into a triggered Plumbix pipeline (WU-045), keeping every job: what Plumbix can run is enabled, the rest is disabled with a reason (WU-044). This unit is the conversion and a preview; writing the files as a change, the screen and re-check are WU-048, templates and richer variables and conditions WU-047.

## Design

- **Source interface.** `importer.Source` has `Name`, `Detect(paths)` (which files are its pipelines) and `Convert(file, content)`, returning a `Converted` pipeline: target name and file, the YAML text, per step its source location and disabled reason, and notes about what did not carry over. `importer.Preview` runs a source over a commit's files. Azure is the first source; GitHub Actions could follow without touching the rest.
- **Step provenance.** A step may carry `source: {file, line, hash}` (format addition): the source file, the line of the job it came from and a SHA-256 of that job's YAML, so re-check (WU-048) can see what changed at the source. Optional, ignored when running.
- **Detection.** A `.yml` or `.yaml` file outside `.plumbix/` and outside any `templates` folder whose top level has `stages`, `jobs` or `steps` and any of `trigger`, `pr`, `schedules`, `pool`, `resources`, `container`. Templates (parameters and steps only) run inside other pipelines and are not imported on their own; a pipeline relying on every default (no trigger, no pool) is not detected. A file that does not parse as YAML is a problem when its name starts with `azure-pipelines`; other unparsable YAML (Helm templates and the like) is ignored.
- **Pipeline name.** The file's base name without `azure-pipelines-` or `azure-pipelines.` prefix and extension, lowercased, non-alphanumerics as dashes (`pipelines/azure-pipelines-orders-api.yml` → `orders-api`, root `azure-pipelines.yml` → `azure-pipelines`); clashes get `-2`, `-3`.
- **Jobs become steps.** An Azure job is one agent running its steps in order on a shared machine; a Plumbix step is one container. So each job becomes one Plumbix step whose `run` lists the job's script steps (`script`, `bash`, `sh`, with `displayName` as a comment line); `checkout: self` is dropped (Plumbix checks out). Step names are `<stage>-<job>` lowercased (`<job>` alone without stages), `-<entry>` per matrix entry.
- **Images.** A job's `container` (a `resources.containers` alias or an image) is the step's image. A job with no container ran on the agent's machine: disabled `host`, the pool noted.
- **Disabled reasons.** `task` (any `task:` step, task names noted), `template` (a `template:` step or job, or `${{ }}` expressions), `checkout` (checking out another repository), `deployment` (a `deployment:` job), `services` (job `services`), `condition` (a `condition` other than `succeeded()`), `variables` (new: `$(...)` macros Plumbix cannot resolve, names noted), `secrets` (a variable group used by the pipeline), `host` (no container). The first reason disables; the note lists all.
- **Variables.** Inline `variables` (map or `name/value` list) become the step's `env`; `$(name)` for such a variable, and `$(Build.SourcesDirectory)`, `$(System.DefaultWorkingDirectory)`, `$(Pipeline.Workspace)`, `$(Build.Repository.LocalPath)` (all `/workspace`) are rewritten to shell form. Any other `$(...)` whose name has a dot (a predefined variable) disables the step with `variables`; a dotless one is left for the shell, as Azure leaves undefined macros, unless a variable group exists, which disables the step with `secrets`.
- **Dependencies.** Jobs in a stage run in parallel unless `dependsOn` says otherwise; a stage depends on the previous one unless `dependsOn` says otherwise, and its jobs need every job of the stages it depends on. Azure stages become Plumbix stages.
- **Matrix.** `strategy.matrix` expands into one step per entry, its variables in `env`.
- **Triggers.** `trigger` branches and paths `include` become `on.push`; a missing `trigger` means every branch; `trigger: none` with no push leaves `on.manual: true`. Excludes are dropped with a note (the pipeline may run more often, never less). `pr` is not imported (a note: `.plumbix/pipeline.yaml` judges changes). Tags, `schedules` and `parameters` disable the pipeline with reason `trigger`, noted. Every imported pipeline also gets `manual: true`.
- **Preview.** `GET /repos/{id}/import?source=azure&branch=` lists, for the branch head, each source file with the converted pipeline (name, file, content, disabled, blockers, steps with reasons and source lines, notes) or its problems. Nothing is written. CLI `plumbix import preview <repo> [--branch b]`.
- Every converted file must parse with `pipeline.ParseTriggered`; a test enforces it over the fixtures. Fixtures are made-up pipelines, never a real project's.
- Also folds WU-051's last nit: the guard's "needs, caches or conditions changed" heading becomes "other settings changed".

## Steps

1. Format: `source`, `variables` reason.
2. `internal/importer`: interface, detection, naming, `Preview`.
3. `internal/importer/azure`: conversion, test first per construct.
4. API, OpenAPI, CLI.
5. Docs.

## Completion

**Delivered**: format `source` and reason `variables` (parser, schema, OpenAPI, web labels); `internal/importer` (`Source`, `Converted`, `Preview`, `PipelineName`, `Slug`); `internal/importer/azure` (detection, triggers, variables, stages and jobs, matrix, containers, every disabling reason, provenance); `Mirror.ListTree`; `Engine.ImportPreview` (YAML files only, 1 MiB each); `GET /repos/{id}/import` with OpenAPI `ImportPreview`; `plumbix import preview`. The guard's heading "other settings changed" (WU-051 nit).

**Evidence**: `TestCIPipeline`, `TestDeployPipeline`, `TestStepsOnlyPipeline`, `TestDetect` over made-up fixtures (every converted file parsed with `ParseTriggered`); `TestPipelineName`, `TestPreviewNamesSortsAndChecks`; `TestStepSource`; `TestListTree`; `TestImportPreview` (engine); `TestImportPreviewEndpoint` (api, OpenAPI); `TestImportPreviewCommand` (cli). A local dry run over a real repository's 25 Azure files (not committed) converted all of them to parsing pipelines, every one disabled as predicted (host, task, condition, checkout, template, deployment), and showed a step template detected as a pipeline, fixed with a test. `make check` green.

**Deferred**: templates, variable groups, richer variables and conditions (WU-047); writing the files as a change and re-check (WU-048).
