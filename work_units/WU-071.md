# WU-071: The review loop clones with the server's credential and gives a review back with a reason

**Status**: ✅ Complete (2026-11-05) · **Features**: F-001, F-010 · **Estimate**: short · **Kai**: HXHA2T (workstream F8QK66, milestone M4 P41048) · **Follows**: WU-070 · **Source**: cabinet.med, the second repository registered on the same server, private on GitHub (reported by its Claude session on 2026-11-05); Q24, A47

## Goal

A private repository the server holds a token for is reviewed by `plumbix review --watch` without any git credential on the loop's machine, and a review the loop cannot answer ends at once with its reason instead of sitting claimed until the step's timeout. Closing a change cancels its run, as the README already said.

## What happened

The server fetched `cabinet.med` fine with the repository's own token (`POST /repos/{id}/token/check` answered ok) and published the review; the loop's `git clone` went out with the machine's git access, anonymous there, and GitHub answered "Repository not found". The loop logged the error and moved on; the claim stayed, the `ai-review` step stayed `running`, and closing the change through the MCP did not end the run either.

## Design

1. **The credential travels with the claim, on request.** `POST /api/v1/reviews/{id}/credential` with the claim's token answers `{user, token}`, exactly what `Engine.auth(repo)` fetches the repository with (the repository's token, else the host's), or 204 when the server fetches anonymously; refused with 404 and 409 like a verdict. It is not part of the brief, so the MCP reviewer and any other claimer see nothing unless they ask; `Engine.ReviewCredential` logs the review and reviewer, never the value.
2. **The loop clones through the askpass script.** `reviewer.checkout` takes the credential and runs every git command with `-c credential.helper=`, `GIT_TERMINAL_PROMPT=0` and `gitops.AuthEnv` (the askpass script written to the loop's work directory with `gitops.EnsureAskpass`), the same path the server uses. Without a credential the user's own git access applies as before. A server that predates the endpoint (404) counts as none.
3. **A review the loop cannot answer goes back with a reason.** `POST /api/v1/reviews/{id}/fail` with the claim's token, `reason` in `review.ReviewerReasons` (`checkout_failed`, `reviewer_error`) and a `message` of at most 2000 characters. `Store.FailReview` closes the claimed review (token checked in the same statement, like a verdict), writes `expired_reason` and the new `expired_message` (migration 0024) and emits `review.expired` with `message`; the waiting step's poll sees the expired review, writes "<reviewer> gave the review back (review X expired: reason)" and the message to the step log, and errors, so the run finishes `needs_human` now. The loop gives back on a failed checkout, a failed Claude run, a non-verdict answer and a verdict refused with 400; a server it cannot reach is reported on stderr and the step waits out its timeout as before.
4. **Closing a change cancels its run.** `Engine.CancelChangeRun(changeID)` cancels the active run with `errClosed` ("cancelled: the change was closed"); the run records cancelled, a waiting review expires `run_cancelled`, the change is left alone. The API close handler calls it after the state change.

## Fixes

**Iteration 1** (`needs_human` on the security risk; three minor findings, all taken): the reviewer's message goes into the step log line by line under the `reviewer:` prefix, as progress lines do, so it cannot pass for the server's own output; a server that answers the credential request with an error (not 204, not 404) gets the review back with `checkout_failed`, where a network error still leaves the step to its timeout; the Expired branch in `waitExternal` uses the give-back wording only for a reviewer's reason and names a platform expiry it finds as such.

**Iteration 2** (`needs_human` on the same risk; one cosmetic note): control characters other than a line break are replaced on intake in `Engine.FailReview`, so a terminal escape in a reviewer's message reaches neither the step log nor the event stream.
