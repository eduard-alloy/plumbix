# WU-003: Container runner and scheduler

**Status**: ✅ Complete with an open security finding (2026-10-16) · **Features**: F-003 · **Estimate**: 4-6 hours

## Goal

Plumbix can execute a parsed pipeline: every step runs in its own container with the workspace mounted, logs are captured, timeouts are enforced, and independent steps run in parallel up to a limit. A test proves whether a step container can reach the Plumbix API on the host.

## Context

- ARCHITECTURE.md: components Scheduler and Runner, A1 (runner behind an interface), A4 (Docker Engine API), section 7 (container isolation), risk 1 (Docker Desktop reaching loopback).
- WU-002: `pipeline.Pipeline` with validated steps and `Order()`.
- Docker 24.0.6 runs locally (API 1.43). Docker commands and tests run outside the Claude Code sandbox.

## Scope

**In**
- `internal/runner`: a `Runner` interface (`Run(ctx, Job) (Result, error)`) and a Docker implementation. A job has image, script, env, workspace, extra mounts, timeout, CPU and memory limits, and a log writer.
  - Pulls the image if missing. Runs `sh -c <script>`, or the image's entrypoint when the script is empty (validators). Working directory `/workspace`.
  - Streams stdout and stderr to the job's log writer.
  - Timeout kills the container and reports `TimedOut`. Cancellation kills it and returns the context error.
  - Containers get `no-new-privileges`, CPU and memory limits, a `plumbix.managed` label, and are always removed afterwards. No Docker socket is mounted.
  - Infrastructure failures (engine down, pull failed) return an error. A non-zero exit is a normal result.
- `internal/scheduler`: executes a pipeline with a `Runner`. Starts steps whose needs succeeded, in file order, at most `MaxParallel` at once. Step outcomes: `succeeded`, `failed`, `timed_out`, `errored`, `skipped` (a need did not succeed), `cancelled`.
- Config: `runner.max_parallel` (default CPU count), `runner.default_timeout` (30m), `runner.step_cpus` (2), `runner.step_memory_mb` (4096).
- `make integration` runs Docker-backed tests (build tag `integration`).

**Out**
- Validator inputs and verdict files (WU-005). Saving evidence and artifacts to disk (WU-005/WU-007). Git worktrees (WU-007). Wiring into the server.

## Acceptance criteria

- **AC-1**: A step's output reaches its log writer and its exit code is reported (integration).
- **AC-2**: A step can write to the mounted workspace and the file appears on the host (integration).
- **AC-3**: A step exceeding its timeout is killed and reported as timed out within a few seconds of the limit (integration).
- **AC-4**: A missing image is pulled. An image that cannot be pulled is an infrastructure error, not a step failure (integration).
- **AC-5**: Env values reach the container (integration).
- **AC-6**: Independent steps run concurrently. `MaxParallel: 1` runs one at a time. Needs are respected (unit, fake runner).
- **AC-7**: When a step fails, steps needing it are `skipped` and independent steps still run (unit).
- **AC-8**: Cancelling the run stops running steps and marks unstarted ones `cancelled` (unit, plus one integration check that the container is gone).
- **AC-9**: Security check: a step container tries to reach an HTTP server bound to the host's 127.0.0.1. The result is recorded either way. If the container can reach it, the work unit still completes, and the finding goes to the user because the fix involves authentication.
- **AC-10**: `make check` and `make integration` pass. No containers labelled `plumbix.managed` are left behind.

## Steps (test first for each)

1. Config fields and defaults.
2. Scheduler with a fake runner: ordering, parallelism, limits, failure propagation, cancellation, default timeout.
3. Docker runner: output and exit code, workspace, env, entrypoint mode.
4. Timeout, cancellation and cleanup.
5. Image pull and pull failure.
6. Security check against host loopback.
7. `make integration`, docs.

**Decisions**
- Docker client: `github.com/moby/moby/client` v0.6.2. It supports engines down to API 1.40, and the local engine speaks 1.43.
- The container wait is registered before start, and wait and logs use their own context, so a cancelled or timed-out job is still killed, drained and removed.
- Containers run with `no-new-privileges`, an init process, CPU and memory limits, and two labels: `plumbix.managed` and `plumbix.job`.
- A missing secret marks its step `errored` without running it. The error names the secret but never shows any value.
- The scheduler never returns an error. Every problem becomes a step outcome.

**Problems hit**
- The leftover-container check first matched every Plumbix container, so it flagged containers from the scheduler's test running at the same time. It now checks only the test's own job label.
- macOS ships GNU make 3.81, which ignores `.SHELLFLAGS`. `make integration` first reported success despite failures. It now uses `set -o pipefail` in the recipe, verified with a deliberately failing test.

**Open security finding**
On Docker Desktop, a step container can reach the Plumbix API on the host's loopback. In v1 there is no authentication, so agent-written code in a pipeline could call the API, for example to merge an approved change or read other runs' logs. On Linux the bridge network cannot reach host loopback, so the exposure is specific to Docker Desktop. The fix needs authentication, which the owner deferred at Q12. The test reports the exposure as a loud skip until a decision is made.
