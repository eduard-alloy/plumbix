# WU-062: Pull-request criteria bound to pipeline steps

**Status**: ✅ Complete (2026-10-29) · **Features**: F-010, F-006 · **Estimate**: one session · **Kai**: BNFQTQ (workstream F8QK66, milestone M2 PZTRDV) · **Follows**: WU-060 · **Source**: Chart-AI's first-day follow-up, ask 1

## Goal

A pull request's criteria (`ParseCriteria`, the list under "Acceptance criteria") are text only. API-submitted criteria carry `check.steps`, which the reference validator proves from step outcomes; a pull request's never do, so every pull-request run says "0 of N met, N not checkable deterministically" and the gate rests on the AI review alone, although build, test and lint ran and passed. Chart-AI records "criteria stated N, assessed deterministically 0" on every pull request.

## Design

- **One form.** A checklist item ending in `(check: build, test)` binds to those steps: `check.steps` as the API carries them, the parenthesis removed from the criterion's text. A leading `build:` token is not a form: it reads like prose ("test: every handler has one"). No command form exists in the parser, so a pull request author can never run a command on the validator; an item that looks like one (`(check: command ...)`, `(run: ...)`) stays text.
- **Known steps only.** Each name must pass `pipeline.ValidStepName` and be a step of the pipeline at the pull request's head (`Engine.PipelineFile` on the head branch, read once per intake or re-parse). Otherwise the item stays a text criterion and carries a `note` ("names step `bulid`, which the pipeline has not"; "names a command, which a pull request cannot run"), a new optional field on `Criterion` (model, OpenAPI, the check-runs contract) that the gate check's criteria table and the change page show. Visible, never dropped, never a failed run.
- **The gate says the split.** The gate check's summary states how many criteria are bound to steps and how many are text for the AI review.
- **Edits follow.** Today an open pull request's change is never updated after intake (`Apply` returns on `found`). Now the title, intent and criteria are compared with the pull request on every sync and on the webhook's `edited` action, and written through `change.Service.UpdatePullRequestText` when they differ; the next run reads them, no run is started by an edit alone.
- **Not in this unit**: a command form (by design, never); binding for API changes (they carry `check` already); Azure DevOps.

## Acceptance criteria

| # | Criterion | Check |
|---|---|---|
| AC-1 | `(check: build, test)` on an item yields `check.steps [build, test]` with the parenthesis gone from the text; items without it stay text; a command-looking item stays text with a note. | `TestParseCriteriaBindsSteps` (pullrequest) |
| AC-2 | A name that fails `ValidStepName` or is not in the head's pipeline leaves the item text with a note naming the step; the note reaches the gate check's criteria table. | `TestParseCriteriaBindsSteps`, `TestOpenBindsCriteriaToThePipeline` (intake, fake engine with a pipeline), `TestGateCheckShowsNotesAndTheSplit` (checkrun) |
| AC-3 | The gate summary says how many criteria are bound to steps and how many are text for the AI review; a bound criterion carries the same `check.steps` an API change does, so the reference validator proves it unchanged. | `TestGateCheckShowsNotesAndTheSplit`, `TestOpenBindsCriteriaToThePipeline` (the change's check) |
| AC-4 | An edited pull request body or title updates the change's title, intent and criteria on the next sync and on the webhook's `edited` action, without starting a run. | `TestEditedPullRequestUpdatesTheChange` (intake), `TestWebhookEditedUpdatesTheChange` (webhook) |
| AC-5 | README Intake, OpenAPI (`Criterion.note`, the form in `acceptance_criteria`), `contracts/github-check-runs.md` and the web change page updated; `make check` green. | `make check` |

## Steps

1. Failing tests: the parser, the intake binding and edit, the gate check, the webhook action.
2. `Criterion.Note`; `ParseCriteria` with the form and a step-existence callback; the intake's binding and `UpdatePullRequestText`.
3. The gate check's notes and split; the webhook's `edited`.
4. Web: the note beside a criterion.
5. Docs.

## Completion

Done 2026-10-29. One thing the ask assumed turned out false: an open pull request's change did not follow title or body edits at all before this unit (`Apply` returned on a found change); `follow` and `UpdatePullRequestText` add that. A closed change keeps its text and a still-open pull request gets a new change, as before. Landed through Plumbix's own merge.
