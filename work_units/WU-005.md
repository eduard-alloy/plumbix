# WU-005: Verdict contract and reference validator

**Status**: ✅ Complete (2026-10-16) · **Features**: F-006 · **Estimate**: 5-6 hours

## Goal

Plumbix publishes what a validator receives and what it must write, can prepare those inputs, can read and check a verdict, and can combine several verdicts into a change outcome. The deterministic reference validator exists as a program and a container image, and an integration test runs it in Docker against prepared inputs.

## Context

- ARCHITECTURE.md 3 (combining verdicts), 4.3 (validator contract), A11 (deterministic reference validator), A12 (AI validator comes next and uses the same contract).
- WU-003: runner jobs take extra mounts. WU-004: `change.Change` with criteria and checks.
- CONSTRAINTS: a validator crash or invalid verdict is never approval. A change touching `.plumbix/` needs a human.
- Wiring validators into a real run (mounting inputs during a pipeline) is WU-007.

## Contracts

**Validator input** (`contracts/validator-input.schema.json`), mounted read-only:
- `/plumbix/in/change.json`: `{"plumbix": "validator-input/v1", change: {id, title, intent, source_branch, target_branch, acceptance_criteria, constraints}, commits: {base, head}, changed_files: [...], iteration, previous_findings: [...]}`.
- `/plumbix/in/evidence/<step>/status.json`: `{"plumbix": "step-status/v1", step, status, exit_code, duration_ms}`, plus `log.txt`.
- `/workspace` read-only. `/plumbix/out/` writable.

**Verdict** (`contracts/verdict.schema.json`), written to `/plumbix/out/verdict.json`:
- `plumbix: "verdict/v1"`, `outcome` (`approve`, `fix`, `reject`), `summary`, `criteria: [{id, status (met, unmet, unknown), reason, evidence}]`, `findings: [{severity (blocker, major, minor), message, criterion, file, line}]`, `risks: [{area, message, human_required}]`, optional `usage: {model, input_tokens, output_tokens}`.
- Rules beyond the schema, checked by Plumbix: criterion IDs must exist in the change and appear once; `approve` may not include an `unmet` criterion; a `fix` must include at least one finding or unmet criterion. A missing, unreadable or rule-breaking verdict is a validator error.

## Combining verdicts

Per criterion across validators: `unmet` if any validator says unmet, otherwise `met` if any says met, otherwise `unknown`. Then, in order:
1. Any `reject`: `rejected`.
2. Any `fix` or any combined `unmet` criterion: `fix_requested`, with every finding.
3. Any validator error, missing required validator, or `unknown` criterion: `needs_human`.
4. A change touching `.plumbix/`, or any risk with `human_required`: `needs_human`.
5. Otherwise `approved`.
The result lists the combined criteria, all findings and risks tagged with their validator, and the reasons for `needs_human`.

## Reference validator

- Reads the inputs. For each criterion: `check.steps` is `met` when every named step succeeded, `unmet` when one failed, timed out or errored, `unknown` when a step has no evidence. `check.command` runs with `sh -c` in `/workspace` with a time limit: exit 0 is `met`, anything else `unmet`. No check is `unknown`.
- Commands run in the validator's own small image with a read-only workspace. They suit file and text checks such as `grep -q retry README.md`. Checks needing the project's toolchain belong in a pipeline step referenced by `check.steps`.
- Risks: changed test files (`area: tests`), changes under `.plumbix/` (`area: pipeline`, `human_required: true`).
- Outcome: `fix` when any criterion is unmet, with one finding per unmet criterion. Otherwise `approve`, even with `unknown` criteria, which the combination still sends to a human. It never rejects.
- Shipped as `validators/reference/Dockerfile`, built from the repo root. A `.dockerignore` keeps `.env`, `bin/` and `.git` out of the build context.

- **AC-1**: Both schemas are published. Contract tests check prepared inputs and example verdicts against them, and the Go verdict checks agree with the schema on every example.

- **AC-3**: Reading a verdict rejects missing files, invalid JSON, schema violations and each extra rule.
- **AC-4**: `Combine` follows the rules above. Each rule has a test, including per-criterion merging and validator errors.
- **AC-5**: The reference validator produces the documented results for steps, commands, missing checks, missing evidence, command time limits and risks (unit tests on the host).
- **AC-6**: Integration: the image builds, runs in Docker with read-only inputs and workspace, and writes a verdict that Plumbix reads and accepts. The runner supports a read-only workspace.
- **AC-7**: `make check` and `make integration` pass. `.env` cannot enter the image build context.

**Decisions**
- A criterion is `met` when any validator says met and none says unmet. That lets the AI validator assess criteria without a deterministic check, while any single `unmet` still wins.
- A change with no validators at all is never approved.
- A validator error does not hide a `fix` from another validator: fixes go back to the author first.
- The reference validator runs commands in its own process group and kills the whole group at the time limit, so a `sleep` child can't hold it.
- The validator image runs as a non-root user. Plumbix must make the output folder writable for it (WU-007).
- `WorkspacePath` now lives in the validator contract too, so the validator binary doesn't pull in the Docker client. A test keeps it equal to the runner's.
- The reference validator and its package are Unix-only (`//go:build unix`), since validators run in Linux containers.
