# WU-082: `plumbix change wait`, the verdict as one blocking command

**Status**: ✅ Complete (2026-11-06) · **Features**: F-004 · **Estimate**: one session · **Kai**: K4NXB7 (workstream XZD9DR, milestone BH0E73) · **Follows**: WU-081 · **Source**: this session's hardening list

## Goal

A script or a person waits for a change's verdict with one command that returns when it is there, says what it is, and exits with a code that scripts can branch on, the way an agent session already does with the MCP tool `wait_for_verdict`.

## What is wrong today

- The MCP tool blocks until the running iteration's verdict or a final state; the CLI has no equivalent. `examples/first-run/first-run.sh` polls `change show` every two seconds, and the owner's sessions used a watcher script outside the repository, over `plumbix events`, which quit early on a stale `needs_human` state and on a run superseded by a newer iteration.
- `plumbix events --change <id>` streams everything and never stops; a script has to parse frames and know which iteration it is waiting for.

## Design

1. **`plumbix change wait <id> [--timeout <duration>]`** in `cmd/plumbix/client.go`, with the MCP tool's semantics: find the running iteration from the change's runs (looking again for a few seconds when the change says running but has no run yet); if none runs, answer at once from the change as it is; otherwise follow `/api/v1/events?change_id=<id>` until `verdict.issued` for that iteration, `change.state_changed` to `merged` or `closed`, or `run.finished` errored for that iteration, bounded by `--timeout` (default 30 minutes, the length of Plumbix's own review step). `Ctrl-C` ends it cleanly.
2. **Output**: one JSON object: `change_id`, `iteration`, `state` (the change's state after the wait), `outcome` and `criteria` (`id`, `status`) from the iteration's result when there is one, `timed_out` when the wait ran out. **Exit code**: 0 approved or merged, 1 fix_requested, rejected or closed, 2 needs_human or escalated, 3 timeout, 1 on any error. A script reads `state` from the JSON either way.
3. **`first-run.sh`** waits with it instead of polling. The README's quickstart and `docs/server.md` list it beside `events`; the usage line names it.
4. **Tests, red first**: a fake server in `cli_test.go` serves the change, its runs and an event stream that issues the verdict for iteration 1 after a moment, and the command prints the state and exits 0; the same server with a silent stream and `--timeout 300ms` exits 3 with `timed_out`; the CLI flow test waits for its first verdict with the command and gets exit 2 for `needs_human`. The first-run integration tests keep passing (`make integration`).
