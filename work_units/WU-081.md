# WU-081: The own-image editor keeps an edit typed the instant its card appears

**Status**: ✅ Complete (2026-11-06) · **Features**: F-004 · **Estimate**: short · **Kai**: J7T5Q8 (workstream XZD9DR, milestone BH0E73) · **Follows**: WU-080 · **Source**: a web test that failed once in Plumbix's own pipeline on 2026-11-06 (run `run_45f6hkylduux`, iteration 3 of WU-077's change) and passed on the rerun

## Goal

A test that fails on timing is a test that will fail again on a slower runner, and here the timing hid a real defect: an edit typed in an own image's Dockerfile editor right after the card appears could be thrown away. The editor keeps every edit; the test that saw the flake reproduces the losing order every time and passes.

## What was wrong

The failed run's DOM dump showed the textarea back on the stored Dockerfile and Save disabled, after the test had typed and clicked. The editor copied the stored file into its draft with `useEffect(() => setText(im.dockerfile), [im.dockerfile])`. When the card appears from a refetch committed outside `act` (the normal case in a browser), that effect is still queued as a task when the next keystroke arrives, and React runs pending passive effects before it renders a keystroke's update, so the copy is enqueued after the edit and wins. In the test suite the window is a race between testing-library's post-wait `setTimeout(0)` and React's scheduler task; locally the scheduler usually wins, on a loaded runner it did not once.

## Design

1. `OwnEditor` derives its draft during render: it remembers the stored file it last saw, and when the prop differs (a save, a reload that brought a different file) it resets the draft in the same render. No effect, no pending task, nothing to race.
2. A test renders the page without `act`, waits one `setImmediate` at a time until the card exists (React's scheduler runs on `setImmediate` under Node, so the commit's passive effects are still queued behind the wait), types, saves, and expects the saved file to hold the edit. Red on the old code with the pipeline's own assertion message; green after.
3. A second test pins the contract from the user's side: an edit survives a refetch that returns the same file (a rebuild of the old file finishes while the person types), and a file the server changed replaces the draft and leaves the editor clean.
