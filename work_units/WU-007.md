# WU-007: Validation loop end to end

**Status**: ✅ Complete (2026-10-16) · **Features**: F-001, F-006, F-015 · **Estimate**: 7-8 hours
**Split**: the event stream moved to WU-014 so this unit fits one session.

## Goal

Submitting a change, or asking Plumbix to validate it again, fetches the code, runs the pipeline in containers, gives each validator its inputs and the diff, runs the validators, combines their verdicts and moves the change to its outcome state. Runs, steps and logs can be read through the API and the CLI.

## Context

- ARCHITECTURE.md 3 (states, fix rounds), 5.1 and 5.2 (flows), A3 (system git), A9 (required validators from the target branch), 6 (files), 7 (crash recovery).
- WU-003 runner and scheduler, WU-004 changes, WU-005 inputs and `Combine`, WU-006 AI validator and `internal/secrets`.
- CONSTRAINTS: validator containers run as non-root, so `/plumbix/out` must be writable by anyone and inputs readable; never mount the data directory; new endpoints go behind the token.
- Out of scope: host credentials and polling (WU-008), merge (WU-010), events (WU-014).

## Design

**Git (`internal/gitops`)**, through the system `git` command with prompts disabled:
- A bare mirror per repo at `<data_dir>/mirrors/<repo-id>.git`, fetched before each run.
- Branch heads, merge base, detached worktree at a commit, diff and changed files from the merge base to the head, reading a file at a commit.
- No credentials yet. Tests use local bare repositories.

**Runs (`internal/store`, migration 2)**: a `runs` table (repo, change, iteration, head, base, status `running|finished|errored|cancelled`, outcome, combined result as JSON, error, timestamps) and a `steps` table (name, validator, status, exit code, duration, error).

**Engine (`internal/engine`)**:
1. `Validate(change)` refuses merged or closed changes, cancels a run still going for that change, records iteration N+1, moves the change to `running`, and continues in the background.
2. Fetch, resolve the source head and target head, compute the merge base.
3. Read `.plumbix/pipeline.yaml` at the head. The required validators are the validator steps in the target branch's version of the file (A9). No file at the target means none are required.
4. Create a worktree at the head under `<data_dir>/work/<run-id>/`.
5. Run the pipeline. Logs go to `<data_dir>/evidence/<run-id>/<step>/log.txt`. Before a validator starts, Plumbix writes its inputs from the steps finished so far, plus the diff and the previous iteration's findings, and mounts them read-only. The workspace is mounted read-only for validators, and the output folder is writable.
6. Read each validator's verdict. A validator step that didn't succeed or wrote no valid verdict is a validator error. Then `Combine`.
7. A fix outcome on iteration 4 or later (three fix rounds) becomes `escalated`. `fix_rounds.max` is configurable.
8. Save steps and result, and move the change from `running` to the outcome, unless the run was cancelled or the change was closed meanwhile.
- Infrastructure failures (git, missing or invalid pipeline file, Docker) mark the run `errored` and the change `needs_human` with the reason. They are never a verdict.
- On startup, runs left `running` become `errored`, and their changes `needs_human`.
- Submitting a change starts iteration 1 automatically.

**Scheduler**: a per-step setup hook, so the engine can prepare validator mounts from the results finished so far.

**API and CLI**:
- `POST /api/v1/changes/{id}/validate` returns 202 with the new run.
- `GET /api/v1/changes/{id}/runs`, `GET /api/v1/runs/{id}` (steps and combined result), `GET /api/v1/runs/{id}/steps/{step}/log` (plain text).
- CLI: `plumbix change validate <id>`, `plumbix run show <id>`, `plumbix run log <id> <step>`.

**Serve**: loads secrets from `secrets_file` (default `<data_dir>/.env`, optional, must be `0600`), creates the mirror, work and evidence folders, and uses the Docker runner.

## Acceptance criteria

- **AC-1**: Git operations work against local bare repositories, including diff and changed files from the merge base.
- **AC-2**: With a fake runner: a passing change reaches `approved`, a failing check reaches `fix_requested` with findings, a revalidation is iteration 2 with the previous findings in its input, and a fourth fix outcome is `escalated`.
- **AC-3**: Required validators come from the target branch's pipeline file. A change that removes a validator still needs it.
- **AC-4**: Missing or invalid pipeline file, unknown branch and runner errors leave the run `errored` and the change `needs_human` with a reason.
- **AC-5**: Revalidating while a run is going cancels the old run, which leaves the change state alone. Closed and merged changes can't be validated.
- **AC-6**: Startup recovery marks interrupted runs `errored`.
- **AC-7**: API and CLI expose runs, steps, results and logs. Responses match the OpenAPI schemas.
- **AC-8**: Integration: a real Docker run with the reference validator image and a local repo ends `approved` for a good change and `fix_requested` for a bad one. Validators really get read-only inputs and workspace.
- **AC-9**: `make check` and `make integration` pass.

**Decisions**
- **Validators run after their needs finish, whatever the outcome.** The first engine test showed the scheduler skipping the validator after a failed test, which turned a fix request into `needs_human`. A failed test is exactly what a validator should judge.
- **Errored steps are infrastructure failures, never a fix request.** If a normal step couldn't run (Docker down, for example), the outcome is `needs_human` with the reason, even if validators asked for fixes.
- A run's workspace is removed before its outcome is recorded, so a finished run never has leftovers.
- A run may only move its change while it is still the change's active run, checked under the lock `Validate` holds.
- The git test helper lives in its own package (`gittest`) so test code never links into the binary.
- The CLI test redirects the GitHub URL to a local repository through git's `url.<path>.insteadOf` environment settings, so it never touches the network.
- The security integration test moved to `internal/api` to break an import cycle (runner test, API, engine, runner).

**Problems hit**
- **Race on revalidation.** Under the load of the full suite, cancelling a run during its git fetch made the fetch fail with "signal: killed". `end()` treated that as an infrastructure error and set `needs_human`, which then blocked the newer run's "approved". Cancellation is now checked before errors. A related window where a superseded run could overwrite the newer run's state is closed by the active-run check. Ten repeated race-detector runs under heavy load passed.
