# WU-048: Import as a change, and re-check

**Status**: ✅ Complete (2026-10-20) · **Features**: F-014, F-004 · **Estimate**: one session · **Kai**: HNQWSN (workstream TCVR9R, milestone I1) · **Decisions**: A36, A37, A38

## Goal

WU-046 and WU-047 convert a repository's Azure pipelines but write nothing. This unit writes them: an import commits one `.plumbix/pipelines/<name>.yaml` per source pipeline on a new branch and opens a Plumbix change for it, which a person approves (every change to `.plumbix/` needs one, and the pipeline guard of WU-051 reports on it). Running the import again is a re-check: it updates what the import owns, keeps what a person edited, and says what changed. It is offered by the API and the CLI; the web button belongs to the Pipelines page (WU-050).

## Design

- **What the import owns** (format addition). The import stamps what it writes, so a later re-check can tell its own content from a person's edits:
  - each imported step's `source` gains `written`: a SHA-256 of the step as written, without its `source`;
  - the pipeline gains a top-level `source: {system, file, written}` (triggered pipelines only): the CI system, the source pipeline file and a SHA-256 of the pipeline's own fields (everything except `steps`, `stages` and `source`).
  - The hash is taken over the parsed content (canonical JSON), so comments, quoting and key order do not count as edits. `written` is optional; content without it counts as a person's.
- **Matching.** An existing file under `.plumbix/pipelines/` on the target branch is the import of a source pipeline when its top-level `source` names the same system and file; so a renamed file is still found. A new pipeline gets its name as in WU-046, avoiding the names of existing files.
- **Re-check, per file.**
  - New source pipeline: the file is added.
  - Pipeline fields: taken from the new conversion when the existing ones are as written, else kept, with a note when they differ.
  - Steps, matched by name: a step as written is replaced by the new conversion; a step a person edited is kept, with a note when its source job changed or is gone; a step without `source` is a person's and is kept; a new job is added; a step as written whose job is gone is removed, unless a kept step needs it.
  - Stages are rebuilt from where each step came from.
  - Notes name each step that now runs, is disabled for another reason, was updated from its source, added, removed or kept.
  - A source pipeline that is gone: its file is removed when everything in it is as written, else kept with a note. A source pipeline that no longer converts keeps its file, with the problem.
  - A file that would not parse after the merge is kept as it is, with a note.
- **Submit.** `POST /repos/{id}/import/changes` (`source`; `target_branch`, `branch`, `title` optional), beside the editor's `POST /repos/{id}/pipeline/changes`, reads the target branch head, plans, commits every added, updated and removed file in one commit on a new branch (default `plumbix/import-<sha>`), opens the change with an intent built from the plan and starts validation. It answers the change and the plan. Nothing to change answers 409 `up_to_date`. The preview (`GET /repos/{id}/import`) gains `files`: the same plan, written nowhere.
- **CLI.** `plumbix import submit <repo-id> [--target b] [--new-branch b] [--title t] [--source azure]`. `--new-branch`, not `--branch`, because `--branch` already means the branch `import preview` reads.
- **Git.** `CommitFiles` commits several files, `nil` content removing one; the editor's single-file proposal uses it. The importer reads YAML blobs in one `git cat-file --batch` instead of one `git show` each (deferred from WU-046).

## Acceptance criteria

1. An import of a repository with no imported pipelines opens a needs_human change adding one file per source pipeline, each stamped with `written` hashes, and the files parse.
2. A re-check with nothing changed answers `up_to_date`; with a changed source job it updates that step; a step a person edited is kept and the note says its source changed.
3. A source pipeline that is gone removes its file when untouched and keeps it with a note when edited; a renamed imported file is still matched.
4. The preview lists the plan per file; the CLI submits; OpenAPI and the pipeline schema describe the additions, and schema and parser agree.

## Steps

1. Schema and parser: pipeline-level `source`, step `source.written`.
2. `importer.Fingerprint`, stamping in `Preview`.
3. `importer.Recheck` with the merge rules.
4. `gitops.CommitFiles`, batch blob reads.
5. Engine plan and submit, API, OpenAPI, CLI.
6. Docs: ARCHITECTURE, CONSTRAINTS, PROJECT, CONTEXT_LOG.

**Deferred**: tag refs for repository resources (with tag triggers, I2 SDJNWE); the import button (WU-050).

## Completion

Delivered 2026-10-20.

- **Format.** `pipeline.Imported` (top-level `source`, triggered pipelines only, refused in `.plumbix/pipeline.yaml`) and `Source.Written`; the schema, its description and the contract examples agree with the parser (`triggered-imported.yaml` stamped, two structural and one cross-field example added).
- **Importer.** `stamp.go`: `Fingerprint` (canonical JSON of the decoded mapping) and `stamp`, called by `Preview` before the parse check. `recheck.go`: `Recheck`, `Plan`, `FilePlan`, `Changed`, `Writes`. When everything in a file is the import's, the new conversion is written byte for byte; otherwise the file is rebuilt from nodes, so a person's comments inside kept steps survive.
- **Git.** `CommitFiles` (removal through `update-index --index-info` with mode 0, because `--force-remove` needs a work tree); `CommitFile` wraps it. `TreeFile.Object` and `ReadBlobs` (one `cat-file --batch`); `yamlFiles` uses them.
- **Engine.** `ImportView.Plan`, computed from the same blobs; `ImportPropose`, `ImportRequest`, `ImportProposal`, `ErrUpToDate`; `pushProposal` shared with `ProposeFile`.
- **API and CLI.** `POST /repos/{id}/import/changes` with the intent built from the plan (files, notes, problems; cut to fit 20,000 characters with "and N more files"), an extra criterion that every job is kept, constraint "only files under .plumbix/pipelines/ change", submitted by `pipeline import`; title "Re-check pipelines imported from ..." once any file existed. Preview gains `files`. `plumbix import submit`. OpenAPI: the endpoint, `ImportFile`, `ImportChange`.
- **Tests first.** Parser (`TestSourceWritten`, red before the parser change), importer (`TestPreviewStamps`, `TestRecheck*`, `TestPlanWrites`), git (`TestReadBlobs`, `TestCommitFilesWritesAndRemoves`), engine (`TestImportPropose`: one commit, needs_human, `up_to_date` once landed, update after a source change), API (`TestImportChangeEndpoint`), CLI (`TestImportPreviewCommand`).
- **Dry run on a real repository** (the Azure files used for WU-047, locally, nothing pushed): 26 pipelines added, all parse; re-check over its own output: 26 unchanged, no notes; with one step edited by hand and another file renamed: still no change, the edit kept and the renamed file matched. It found one bug: a file with a duplicate key was merged with a misleading note; now such a file is left as it is (test added).
- **Not done here.** The browser button (WU-050). Tag refs for repository resources move to I2 with tag triggers. No import was submitted to a real repository: that pushes a branch to its host and is the owner's call.

## Fixes

- 2026-10-20, review of the landing change (approved, 4 minor findings):
  - A re-check commit carried the message "Import pipelines from ..." while the change was titled "Re-check ...". `ImportRequest.RecheckMessage` is used once any file was imported before (`Plan.Recheck`), and the change takes the commit's message as its title.
  - A second file naming the same source pipeline was silently ignored. It is now listed as `kept`, with a note naming the file that is the import.
  - A local variable named `os` in `merge` is renamed `was`.
  - Not changed: when opening the change fails after the branch was pushed, the branch stays on the host and a retry with the default name gets `branch_exists`. The error names the branch, so it can be deleted or another name given; cleaning up a pushed branch on a failure would need a delete-branch operation on every host.
- 2026-10-28, review of the landing iteration (approved by a person after main moved; 5 minor findings, 3 distinct):
  - `TestOneBuildAtATime` (images) was flaky: its last build kept writing into the temp directory after the test returned, so the cleanup raced it (seen once in the pipeline, not in 40 local runs). The test now waits for that build. Pre-existing since WU-035.
  - `CommitFiles` removed a file with a 40-character zero object id, wrong for a SHA-256 repository. It now sizes the id by `rev-parse --show-object-format`, tested on a mirror cloned from a SHA-256 remote. Found on the way: `Fetch` initialises the mirror as SHA-1, so a SHA-256 repository cannot be fetched at all ("mismatched algorithms"); recorded in CONSTRAINTS as a known limitation, full support is its own work unit.
  - Not changed, as before: a branch left on the host when opening the change fails after the push. The error names the branch; cleanup waits for a delete-branch operation on every host.
