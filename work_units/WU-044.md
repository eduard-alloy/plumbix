# WU-044: Disabled steps

**Status**: ✅ Complete (2026-10-19) · **Features**: F-002 · **Estimate**: one session · **Kai**: 0KK3K9 (workstream TCVR9R, milestone I1) · **Decisions**: A36, A37

## Goal

Pipeline import (A36, A37) brings every step of a source pipeline into Plumbix, including steps Plumbix cannot run yet. This unit gives the pipeline format a way to hold such a step: it stays in the file, disabled, with a reason from a published list. A pipeline with any disabled step is disabled and never runs; the editor shows which steps block it and why. A person can also disable a step by hand.

## Design

- **Format.** A step may carry `disabled: {reason: <code>, note: <text>}`. `reason` is required and comes from a fixed list; `note` is optional free text (at most 500 characters). A disabled step needs neither `image` nor `run`, since an imported source task may have neither; every other field keeps its rules, and `needs` still has to name existing steps.
- **Reasons.** `user` (disabled by a person), `docker` (uses Docker itself), `services` (needs service containers beside it), `host` (runs on the agent's machine, no image), `task` (a source CI task with no Plumbix equivalent), `template` (comes from a template Plumbix could not read), `condition` (a run condition Plumbix cannot express), `checkout` (needs another repository checked out), `deployment` (deploys to an environment or waits for an approval), `secrets` (needs variables or secret groups not mapped to Plumbix secrets). The list lives in `pipeline.Reasons` and in the schema's enum; a test keeps them equal. Later units add codes as importers need them.
- **Disabled pipeline.** `Pipeline.Disabled()` is true when any step is disabled; `Blockers()` counts steps per reason. The engine's `readPipeline` refuses a disabled pipeline with an error naming the reasons, so a change's run errors and the change goes to needs_human like any pipeline the operator must fix, and a branch run errors the same way. Nothing reaches the runner.
- **API.** `PipelineStep.disabled` (`{reason, note}`, absent when enabled) and `PipelineModel.disabled` (boolean). `POST /pipelines/check` adds `disabled` and `blockers` to a valid result.
- **Editor.** `PStep.disabled` is owned by the editor (in `STEP_KEYS`, written by `desired`); a disabled step with no image writes none. Disabled cards are dimmed and labelled with the reason; a notice above the canvas says the pipeline is disabled and lists the blocking reasons with counts. The inspector shows the reason and note; a "Disabled" switch disables a step with reason `user` and re-enables a `user`-disabled step. A step disabled for any other reason cannot be switched on from the editor: the inspector says Plumbix cannot run it yet.

## Acceptance criteria

| # | Criterion | Check |
|---|---|---|
| AC-1 | A step with `disabled` and a known reason parses without image or run; an unknown reason, a missing reason, a long note or an unknown key under `disabled` is refused. Schema and parser agree. | pipeline tests, contract test |
| AC-2 | `Disabled()` and `Blockers()` report a pipeline with disabled steps. | pipeline test |
| AC-3 | A change whose pipeline is disabled errors and ends needs_human with the reasons in the error; no step runs. A branch run errors the same way. | engine tests |
| AC-4 | The pipeline API and the check endpoint report disabled steps and the disabled pipeline, matching the OpenAPI schema. | api tests |
| AC-5 | The editor keeps `disabled` through a save, writes no empty image for a disabled step, dims disabled cards, shows the notice, and switches `user` disabling on and off. | vm and page tests, screenshot |
| AC-6 | `make check` passes; ARCHITECTURE, CONSTRAINTS, PROJECT and CONTEXT_LOG describe it. | |

**Delivered**: `pipeline.Disabled`, `Reasons`, `Pipeline.Disabled()`, `Blockers()`, `BlockerSummary()` and the parser rule (`internal/pipeline/disabled.go`); the schema's `disabled` with its enum and the relaxed image and run rules; the refusal in `engine.readPipeline`; `disabled` on the API's pipeline model and step and `disabled`/`blockers` on the check result, in OpenAPI; in the web, `PStep.disabled`, `REASONS`, `blockers`, `toggleDisabled`, the writer and edit summary, dashed and dimmed cards with the reason on the command line, the notice above the canvas and the inspector's block or switch.

**Evidence**: `disabled_test.go` in pipeline (parsing, errors, schema and OpenAPI reason lists), engine (no step runs; change ends needs_human; branch run errors) and api (pipeline endpoint and check, against OpenAPI); `vm/disabled.test.ts` (read, byte-identical save around disabled steps, writer, user toggle); three page tests. Before the guard, the engine test showed a disabled step with no image being run. Screenshots in both themes of the page with two disabled steps (through a proxy that marks them, since main has none). `make check` green.

**Also fixed**: the Pipelines page kept its own `repoName` and showed URL-encoded names (`%20`) in its tabs; it now uses the shared one (page test).
