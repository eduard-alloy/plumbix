# WU-011: Web interface, core screens

**Status**: ✅ Complete (2026-10-16) · **Features**: F-004 · **Estimate**: 8 hours

## Goal

The first half of the interface from `web/design`: the app shell, the state encoding, the sign-in page, the changes list with keyboard and live updates, and the change screen with intent, criteria, verdict, findings, risks, iterations, evidence and the merge action with its refusal notices. A developer can supervise agents from the browser; logs, the diff view, alerts and repositories follow in WU-017.

## Context

- `web/design/README.md` is the spec (measurements, copy, behaviour); `web/design/design/Plumbix.dc.html` holds the view models the screens compute. `tokens.css` is used as is.
- WU-016 provides sign-in, the diff endpoint and serving. Decisions: Close is an inline two-step confirm; Validate again says "Validating again" and goes live.
- The API's run carries no steps until it finishes; this unit records steps as they finish so a running change shows progress.

## Design

**Structure.** `web/src`: `api.ts` (typed fetch, 401 → signed out), `model.ts` (API shapes), `format.ts` (durations, ages), `router.ts` (pathname routing, `/`, `/changes/:id`, `/login`, `/alerts`, `/repos`), `store.tsx` (one context: repos, changes, runs per change, alerts, last event; loaded once, patched by refetch on events), `events.ts` (EventSource; browsers resend `Last-Event-ID` on reconnect), `vm/changes.ts` and `vm/change.ts` (pure view models, tested without the DOM), components under `ui/` and `pages/`.

**Live.** Every event names its change or run. The store refetches that change and its runs (debounced per change), alerts on alert events, and shows the last event in the sidebar. Elapsed times tick client-side from `started_at`.

**Running changes.** The engine now records each step as it finishes (`run.Store.RecordStep`), so `GET /runs/{id}` lists finished steps mid-run and the verdict panel shows the pipeline progressing. Which step is running is not known (several may run at once); rows show `iteration N · elapsed`.

**Actions.** Merge posts and either shows the merged change or a notice for `source_moved`, `target_moved`, `push_rejected`, `invalid_state` with the design's copy and next step. Close is an inline confirm (`Close` → `Close this change?` `[Confirm] [Keep]`). Validate again posts and the page goes live.

**Deferred to WU-017.** The step log panel (evidence links open the raw log in a new tab for now), diff hunks with inline findings (the Diff section shows the stat summary and, on load, the file list), alerts and repositories pages (navigation and counts exist; the pages show a one-line note), the design-system page.

**Testing.** Vitest with jsdom and Testing Library. Pure view models and formatting are tested directly; pages are tested against a stubbed `fetch` and `EventSource` with API-shaped fixtures. `make test` runs them with the Go tests; `make web` typechecks and builds.

**Decisions**
- Running changes show `iteration N · elapsed`, not the current step: the scheduler may run several steps at once and the API does not say which. Finished steps appear as they end.
- Iteration duration is wall-clock from start to finish, not the sum of step durations: it is what the person waited for.
- The store refetches what an event names instead of patching from payloads. Simpler, always consistent with the API; the cost is one or two small requests per event.
- Evidence and verdict step links open the raw log in a new tab until the log panel arrives (WU-017). The Diff section shows the stat summary and, on load, the file list; hunks and inline findings are WU-017.
- The list's filters live in the URL query so a reload keeps them.

**Not verified in a browser**: this unit was built headless. The component tests cover behaviour and copy; the first visual pass against the handoff happens when you open it. Expect small spacing fixes.
