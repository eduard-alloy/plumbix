# WU-080: Run evidence shows steps grouped by stage

**Status**: ✅ Complete (2026-11-06) · **Features**: F-004 · **Estimate**: one session · **Kai**: 1KCENW (workstream XZD9DR, milestone BH0E73) · **Follows**: WU-078 (closed) · **Source**: deferred from WU-020 (2026-10-17)

## Goal

On the change page, the evidence list and the verdict panel show the run's steps under their stage, the way the pipeline editor draws stages as bands, so a reader sees "checks: four steps, 1m 19s, all succeeded" before the four rows, and a failed stage reads as one failure rather than four lines to scan.

## What is wrong today

- The run records carry each step's stage (`run.Step.Stage`, set from the pipeline file's `stages` since WU-019), and the change view model copies it onto every step row (`StepVM.stage`), but nothing reads it: the evidence section maps the steps to flat rows, and the verdict panel's step list is flat too.
- The pipeline editor already draws a stage as a band with its name (WU-038); the change page gives the same pipeline no structure.

## Design

1. **View model** (`web/src/vm/change.ts`): a `stageGroups(steps: StepVM[]): StageGroupVM[]` that walks the steps in run order and groups each staged step under the stage of its first appearance; an unstaged step is a group of its own with no stage row. A group with a stage carries `stage: { name, dur, status, count }`: `dur` is the longest step's duration (steps run in parallel inside a stage, so the longest one is the stage's wall time), `status` the worst status by the order `failed, errored, cancelled, running, queued, skipped, succeeded`, and `count` the number of steps. The evidence section and the verdict panel both expose `groups` beside the flat `steps` they expose today, so nothing else changes.
2. **Change page** (`web/src/pages/ChangePage.tsx`): the evidence list renders a stage row (`div.stage-row`, `aria-label="Stage <name>"`: status icon, name, "N steps", longest duration) above the rows of its steps, which get the class `staged` for a small indent; the verdict panel does the same with `div.vstage` above its `vstep` buttons. A step without a stage renders exactly as today. The stage row is not a button and has no log; the step rows under it keep theirs. Validators get a stage row too when the pipeline file names one for them, since the grouping reads the step's stage and nothing else.
3. **Styles** (`web/src/app.css`): `.stage-row` and `.vstage` as quiet rows, name in the mono face, count and duration in the dim colour; `.step.staged` and `.vstep.staged` indented by the icon width.
4. **Fixtures and tests**: the fixtures' `okSteps` and `fixSteps` put `build`, `test` and `lint` in the stage `checks`, as Plumbix's own pipeline does; the errored run fixture keeps its unstaged `build`. Tests: on an approved change the evidence list shows the `checks` row with three steps and the longest duration before the `build` row, and no stage row in the verdict panel (its validators are unstaged); on a running change the verdict panel's pipeline list shows the `checks` row; on the errored change nothing is grouped and the rows are as before. Existing tests that count `button.step` are untouched, since a stage row is a `div`.
