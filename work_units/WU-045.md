# WU-045: Pipeline files with triggers

**Status**: ✅ Complete (2026-10-19) · **Features**: F-002, F-014 · **Estimate**: one session · **Kai**: X82KRV (workstream TCVR9R, milestone I1) · **Decisions**: A36, A37

## Goal

Import (A36) turns each source pipeline into its own file under `.plumbix/pipelines/`, each started by its own triggers. This unit lets Plumbix read and run those files: on a push to a matching branch, or by hand. `.plumbix/pipeline.yaml` stays the pipeline that judges changes, unchanged. The web page for several pipelines is WU-050.

## Design

- **Files.** Every `.plumbix/pipelines/<name>.yaml` at a commit is a triggered pipeline; `<name>` follows the step name rules. Other files in the folder are ignored.
- **Format.** A triggered file is format v1 plus a required `on` and an optional pipeline-level `disabled`:

  ```yaml
  version: 1
  on:
    push:
      branches: [main, "release/*"]   # globs, as in when.paths
      paths: ["services/claims/**"]   # optional
    manual: true
  disabled: {reason: trigger, note: "tags: v*"}
  steps: ...
  ```

  `on` needs `push`, `manual` or both. A triggered file holds no validators: validators judge changes and belong in `.plumbix/pipeline.yaml`. `.plumbix/pipeline.yaml` refuses `on`. `disabled` at the top takes the step reasons plus a new `trigger` (started in a way Plumbix cannot run yet, such as tags, schedules or manual parameters). A pipeline is disabled when it or any step is.
- **Push.** On every branch head the poller sees move, including Plumbix's own merges and change branches, the engine reads the triggered files at the new head and starts a run of each enabled one whose `push.branches` match the branch and, when `paths` is set, whose paths match a file changed since the previous head (a new branch always matches). Runs are pinned to that commit. A disabled or invalid file starts nothing and is logged. The existing plain run of `.plumbix/pipeline.yaml` is unchanged.
- **Manual.** `POST /repos/{id}/pipelines/{name}/runs` with `{branch}` (default: the repository's first protected branch) runs the pipeline at the branch head. Refused with 404 when there is no such file, 409 `pipeline_disabled`, `not_manual` or `pipeline_invalid` otherwise. CLI: `plumbix pipeline run <repo> <name> [--branch b]`.
- **Listing.** `GET /repos/{id}/pipelines?branch=` lists the triggered pipelines at the branch head: name, file, triggers, disabled, blockers, problems.
- **Runs.** A run records the triggered pipeline it ran (`pipeline`, empty for the change pipeline); `run.started` carries it. The editor's last-run durations come only from runs of the change pipeline.
- **Images.** The Images page also counts images named by triggered pipelines.

## Fixes
- 2026-10-19, review of the landing change (iteration 1, needs_human on risk 7, which stays the owner's): a pipeline-level `disabled` was accepted in `.plumbix/pipeline.yaml` too; it is now only for triggered files (contract file `disabled-in-change-pipeline.yaml`). The poller called `RunPushed` once per moved branch, each fetching; it now passes all moves of one poll as `[]run.Move` and the engine fetches once. A failed pipeline or move no longer stops the others; errors are joined and logged. The Images page read triggered pipelines with a second fetch and dropped failures silently; it now reads them at the head `PipelineFile` just fetched (`Engine.TriggeredAt`), logs failures, and still counts them when the change pipeline does not parse.
- 2026-10-19, iteration 3 (fix_requested): the major findings described A38's intended behaviour (change and branch runs get no secrets off protected branches) against an intent written before it; the change was resubmitted with an intent and criteria that state it. Also: A36 to A38 recorded in DISCOVERY.md (Q20, Q21); the branch is passed to `schedulerOptions` instead of overwriting the run's; `ListFiles` checks the ls-tree fields before reading them.
- 2026-10-19, review of c_gzx3vjytqxhi (approved): an API test now pins an unknown branch on a manual run to 404 not_found.
