# WU-027: Live steps and external review progress

**Status**: ✅ Complete (2026-10-18) · **Features**: F-003, F-004 · **Estimate**: 1 session · **Kai**: AXBM9M

## Goal

While a reviewer works, the change page shows it working. Today a step exists in the run record only once it ends, so the external step's log, and every other running step's log, cannot be opened until the step is over, and the external log sits at "claimed by" for minutes anyway. After this unit a running step is listed with a live log, and `plumbix review --watch` posts short progress lines as Claude Code reads files and runs commands.

## Design

**Running steps.** The scheduler gets a `Started` hook beside `Finished`. The engine records the step as `running` when it starts (the record is replaced when it ends, as today) and emits `step.started`. The API already serves a running step's log file; the web store refetches the run on `step.started`, the step rows show running steps with the running pill, and the log panel follows a running step: it refetches the log every two seconds and keeps the view at the bottom until the step ends.

**Progress lines.** `POST /api/v1/reviews/{id}/log` `{token, line}` appends a line to the waiting step's log, prefixed `reviewer:`. The review must be claimed with that token. Lines are trimmed and bounded (300 characters, 300 lines per review, no more than two per second; beyond that 429), so a reviewer cannot flood a log. 204 on success.

**The loop.** `plumbix review` runs Claude Code with `--output-format stream-json --verbose` and reads the stream: each assistant tool use becomes a progress line (`turn 3: Read internal/engine/external.go`, `turn 5: Grep ReleaseReview`, `turn 7: Bash go test ./internal/store/`), posted as it happens and rate-limited client-side; the final `result` object is parsed as before. A fake `claude` that prints one JSON object still works, so the existing tests hold.

## Completion

**Delivered**: scheduler `Options.Started`; the engine records a step as `running` when it starts and emits `step.started` (schema, store lifecycle test, web event type); `Engine.AppendReviewLog` with the bounds (300 characters, 300 lines, one every 500 ms) behind `POST /api/v1/reviews/{id}/log` (204, 400 problems, 404, 409 wrong token or not claimed, 429 `too_many`) in OpenAPI; `plumbix review` runs `claude --output-format stream-json --verbose`, reads the stream as it arrives and posts each tool use as `turn N: Read <path>` / `Grep <pattern>` / `Bash <command…>`, rate-limited at 600 ms, the final result parsed as before; the web step rows show running steps with the running pill and an open log, the log panel follows a running step (refetch every 2 s, view kept at the bottom, "The log follows until the step ends") and fetches the final log once the step ends; ARCHITECTURE (API table, 4.3, 4.4, A16), CONSTRAINTS, PROJECT, CONTEXT_LOG.

**Evidence**: `TestStartedHookSeesEveryStepThatRuns` (scheduler); `TestARunningStepIsRecordedWhenItStarts`, `TestAReviewerAppendsBoundedProgressLines`, the event-order tests now expecting `step.started` (engine); `TestAReviewerPostsProgressLines` and the stream replay test (api); `TestStreamedToolUsesBecomeProgressLines` with a streaming fake `claude` (reviewer); `TestLifecycleEmitsEvents` (store); the running-change page test and "follows a running step, refetching the log, until the step ends" (web). `make check` green.

**Decisions made here**: progress goes into the step log file rather than a new table, so the existing log endpoint, panel and download serve it; the bounds are fixed constants, not settings; the loop limits itself below the server's rate so an honest reviewer never sees 429; a running step shows no exit code or duration rather than a guessed one.

**Deferred**: a streamed log endpoint (the panel polls); progress lines from the container AI validator (it has no claim token; it could log to its own stdout instead).
