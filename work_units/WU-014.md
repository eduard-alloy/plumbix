# WU-014: Event stream

**Status**: ✅ Complete (2026-10-16) · **Features**: F-001 · **Estimate**: 5-6 hours

## Goal

Clients learn what Plumbix did without polling. Every change of state is an event with an increasing id, kept in the store and streamed over Server-Sent Events (SSE) at `GET /api/v1/events`. A client that reconnects with the last id it saw gets everything it missed. The web interface (WU-011) and external clients such as Kai build on this.

## Context

- ARCHITECTURE.md 4.4 (events), 4.1 (`GET /api/v1/events`), A5 (SSE with resumable ids), `contracts/events.schema.json`.
- Split from WU-007. Every producer of events already exists: change service (WU-004), engine and runs (WU-007), merges and alerts (WU-010).

## Design

**The store is the event source.** Every store write that changes something a client cares about appends an event row in the same transaction: `CreateChange`, `SetChangeState`, `CreateRun`, `FinishRun`, `RecordMerge`, `Raise`, `Resolve`, `ResolveKey`. Services and the engine do not emit events themselves, so no write path can forget one and a crash can never leave data without its event. The one event with no write of its own, `step.finished`, is appended by the engine through `AppendEvent`. Emitting writes hold one mutex from before the transaction until after the fan-out, so live subscribers see ids in order.

**Envelope.** `{id, type, time, repo_id?, change_id?, run_id?, payload}`. `id` is an `INTEGER PRIMARY KEY AUTOINCREMENT`, so ids grow and are never reused. The three optional ids are filter keys; the payload holds what the type needs:

| Type | Payload |
|------|---------|
| `change.submitted` | `source_branch`, `target_branch`, `title`, `submitted_by?` |
| `change.state_changed` | `from`, `to` |
| `change.merged` | `branch`, `commit`, `previous`, `strategy` (run_id = merged run) |
| `run.started` | `branch`, `iteration?` |
| `step.finished` | `step`, `validator`, `status`, `exit_code`, `duration_ms`, `error?` |
| `run.finished` | `branch`, `iteration?`, `status`, `outcome?`, `error?`, `head`, `base` |
| `verdict.issued` | `iteration`, `outcome`, `criteria[{id, status}]`, `findings` (count), `reasons[]` |
| `alert.raised` | `alert_id`, `kind`, `key`, `message` |
| `alert.resolved` | `alert_id`, `kind`, `key` |

`iteration.started` from the architecture draft is dropped: a change's run *is* its iteration, and `run.started` carries `change_id` and `iteration`. `alert.resolved` is added so an interface can drop an alert live.

**Hub.** `events.Hub` fans events out to subscribers over buffered channels and never blocks a writer. A subscriber whose buffer fills is marked lagged and its channel closed; it resumes from the store. `Hub.Close` ends every subscription, which is how the server stops open streams at shutdown.

**Stream.** `GET /api/v1/events?repo_id=&change_id=&after=` with `Last-Event-ID` overriding `after`. The handler subscribes first, replays from the store everything after the last id in batches, then streams live, skipping ids it already sent. A lagged subscription loops back to replay. A comment line every 15 seconds keeps the connection alive. Frames are `id: N`, `event: <type>`, `data: <json envelope>`. Bearer token as everywhere; an unparsable id is `invalid_request`.

**Client and CLI.** `internal/client` gets `Stream`, a small SSE reader. `plumbix events [--repo <id>] [--change <id>] [--after <id>] [--max <n>]` prints one JSON envelope per line until interrupted or `--max` events were printed.

**Contract.** `contracts/events.schema.json` describes the envelope and every payload with `oneOf` over types. The contract test drives a full lifecycle through the real store and checks every produced event against the schema, and that the schema's type list and the Go constants are the same set.

**Not in scope.** Pruning the events table (none in v1; a note in CONSTRAINTS), outgoing webhooks (need authentication first), a plain JSON listing of events (the stream with `after` covers it).

## Acceptance criteria

- **AC-1**: A change lifecycle through the store (submit, run started, step, run finished with verdict, state change, merge, alert raised and resolved) produces one event per fact with strictly increasing ids, and every event validates against `contracts/events.schema.json`.
- **AC-2**: Hub subscribers receive events in id order, filtered by repo or change; a slow subscriber is marked lagged instead of blocking the writer; closing the hub ends every subscription.
- **AC-3**: `GET /api/v1/events` replays events after `Last-Event-ID` (or `after`), then streams live ones with no gap and no duplicate; filters apply to both; heartbeats are sent; the stream needs the token.
- **AC-4**: An engine run emits `step.finished` for every step and the whole sequence (`run.started` … `change.state_changed`) arrives on the stream through the real server.
- **AC-5**: `plumbix events` prints envelopes as JSON lines and honours `--after` and `--max`.
- **AC-6**: `make check` and `make integration` pass.

**Decisions**
- A16: the store is the event source (Kai 01M52WMTTV97PBCY4N7SSHKFSK). A first CLI attempt at recording it mis-typed `--why` for `--body` and left entry 01M52WKYFSJYQPN9SSXWKJ9PM0 with the why inside its title; the proper entry names it.
- `iteration.started` dropped, `alert.resolved` added (see Design).
- Events are notifications, never pruned in v1, and the API stays the source of truth. A plain JSON listing was left out: the stream with `after` and `--max` covers it.
- `events.SubscriberBuffer` is a variable so the API test can shrink it and drive the lag path.
