# WU-054: The gate on GitHub pull requests

**Status**: ✅ Complete (2026-10-28) · **Features**: F-010 (first slice), F-005 · **Estimate**: one session · **Kai**: XQHDGN (workstream F8QK66, milestone M2 PZTRDV) · **Decisions**: polling first with a webhook beside it, GitHub merges PR-fronted repositories, criteria under an "Acceptance criteria" heading, `plumbix/<validator>` and `plumbix/gate` check runs with a marked JSON block (Kai decision 01M6174SGCKBEYGC5M1S79YE4F)

## Goal

Plumbix runs beside a GitHub pull request instead of replacing it: validators run on the PR, every verdict lands as a check run that carries the structured verdict, the hold is a required check, a review approval by a person counts as Plumbix's own approval, and GitHub merges. Chart-AI then reads the governed-path contract from GitHub's own surfaces. The shape where Plumbix merges stays available per repository.

## Design

- **App identity** (`internal/host/githubapp.go`): `PLUMBIX_GITHUB_APP_ID` and `PLUMBIX_GITHUB_APP_KEY` (the PEM, pasted with `\n` for its line breaks or base64-encoded) make a `GitHubApp`; it signs an RS256 JWT with the standard library, finds the installation for a repository and mints an installation token, cached until a minute before expiry. `GitHub.Auth` keeps the PAT path first and falls back to the App's token; `TokenExpiry` checks the App when there is no PAT. `PLUMBIX_GITHUB_WEBHOOK_SECRET` verifies webhook deliveries.
- **Repository settings** (`change.Repo`): `pull_requests` opts a GitHub repository into PR intake; `merger` is `plumbix` or `github`, defaulting to `github` when `pull_requests` is set and `plumbix` otherwise, so existing repositories do not change.
- **Pull requests as changes** (`internal/pullrequest`): the poller calls `Syncer.Sync` for each opted-in repository; the webhook handler (`POST /api/v1/hooks/github`, HMAC-SHA256, no bearer token) feeds the same code with one PR. An open PR against a branch becomes a change with the PR title, body as intent, criteria from a list under an "Acceptance criteria" heading (none when the body states none, the one case a change may have no criteria: the gate check says so and the validators judge the intent and the diff), `submitted_by` as the GitHub login or `app/<slug>` for an App, and `pull_request: {number, url}`. PRs from forks are skipped and logged, since their head is not a branch of the repository. Pushes to the PR branch revalidate through the existing poller path. A closed PR closes the change; a merged PR records the merge.
- **Check runs**: one `plumbix/<validator>` per validator with a verdict (conclusion from the verdict's outcome, criteria as a table, the verdict JSON between `<!-- plumbix-verdict/v1 -->` and `<!-- /plumbix-verdict -->` in `output.text`) and one `plumbix/gate` (conclusion from the change's state: approved → success, rejected or fix_requested → failure, needs_human or escalated → action_required; the combined run result between `<!-- plumbix-result/v1 -->` and `<!-- /plumbix-result -->`). The gate is `in_progress` while a run goes. The publisher subscribes to the event hub (`run.started`, `run.finished`, `change.approved_by_person`). Documented in `contracts/github-check-runs.md`.
- **The hold**: the enterprise marks `plumbix/gate` required. A GitHub review in state `APPROVED` on the validated head by a user (not a bot) whose `author_association` is `OWNER`, `MEMBER` or `COLLABORATOR` counts as `ApproveByPerson` with the reviewer's login and body as the reason; the gate then turns success. Anyone can review a public repository, so other associations are logged and ignored. Plumbix's own approval still works.
- **The merge**: `merger: github` means GitHub merges pull requests; `Engine.Merge` refuses a PR change on such a repository and says so. On a merged PR, `Engine.RecordExternalMerge` fetches the mirror, works out the target's previous head from the merge commit (first parent of a merge commit; for one-parent commits, the rebased range when the PR's commits match by subject and author, else the squash's parent), records the merge with strategy `github` and `merged_by`, records the pipeline files as approved, and moves the change to merged. Changes without a PR still merge through Plumbix.
- **Alerts**: `gate_bypassed` when a PR merges while its change was not approved (reason `not_passed`) or while `plumbix/gate` is not a required check on the target (reason `not_required`, read from the rules and branch-protection endpoints; unknown when the App may not read them, and then no alert). The poller's `bypass_commit` stays for commits outside any recorded merge.
- **Events**: `change.submitted` gains an optional `pull_request` object, `change.merged` gains `merged_by` and the strategy `github`, alert kinds gain `gate_bypassed`. All additive.

## Fixes

**Iteration 1** (`fix_requested`, 11 findings from the three AI validators, all taken):
- Only an approving review whose `author_association` is OWNER, MEMBER or COLLABORATOR counts as a person's approval (`host.Review.MayApprove`); anyone can review a public repository. Test: a NONE and a CONTRIBUTOR approval are ignored.
- `FromSecrets` keeps the App construction error (`GitHub.AppErr`) and `TokenExpiry` reports it, so a malformed key no longer leaves fetches silently anonymous.
- `GateApproved` returns `ok` false without an approval instead of reading a nil pointer.
- Branch names are path-escaped in `RequiredChecks` (tested with `release/2026`).
- `Repo.merger` stays optional in the OpenAPI schema so repository objects recorded before this unit still validate; the server always sends it.
- A ping delivery answers `{"handled": false}` as the contract says.
- `ListPullRequests` follows pagination up to ten pages (a risk the validators noted).
- Docs: the work unit's design text and AC-4 test names matched the code; the draft sentence in `contracts/github-check-runs.md` moved out of the "nothing" list.

**Iteration 2** (`approved`, two doc nits): ARCHITECTURE 5.5 step 3 now names the `author_association` rule.

**Iteration 3** (`needs_human`): all four validators approved, but the three AI reviews carried no per-criterion statuses, so six criteria read as unknown. Revalidated once as a validator quirk.

**Iteration 4** (`escalated`: a fix after three fix rounds; one major, five minor, all taken):
- `RecordExternalMerge` recorded the merged pipeline files as approved whatever the change's state, so a merge past the gate could launder a pipeline file into one that gets secrets (A38). Now only an approved change's files are recorded; otherwise `pipeline_unapproved` is raised. Test: `TestExternalMergePastTheGateApprovesNoPipeline`, bypassed and approved.
- Review states compare case-insensitively: the REST API says `APPROVED`, webhook deliveries say `approved`; the webhook test uses the webhook's casing.
- `ListReviews` follows pagination like `ListPullRequests`.
- The merge endpoint's 409 codes name `github_merges`.
- The publisher's map of running gates is bounded (256 entries).
- Loosened contract rules, called out here as the changelog: `change.merged` no longer requires `run_id` (absent when GitHub merged before any run), and a `Change` response may carry an empty `acceptance_criteria` (a pull request that stated none). Every payload produced before this unit still validates.

The change escalated on Plumbix's three-round rule, so after these fixes a person validated it again (iteration 5) and merged it.

**Iteration 5** (`needs_human`: every validator approved, every criterion met; ai-review asks a person to sign off the new credential and the review-approval rule, which is the owner's call; three minor findings taken):
- Pipeline approvals on a GitHub merge now require the approval to cover the merged head: the latest finished run's head, or the person's approved head (`approvalCovers`). A commit pushed after the approval and merged before Plumbix judged it records nothing and raises `pipeline_unapproved`. Test: `TestExternalMergeApprovalMustCoverTheHead`.
- `pipeline_unapproved` on a merge past the gate is raised only when a pipeline file landed (`touchesPipeline`); `gate_bypassed` covers the rest. Test: `TestUnapprovedExternalMergeWithoutPipelineFilesIsQuiet`.
- `TestGitHubAppRefreshesExpiredTokens` moves the App's clock past the refresh margin and sees a second mint.
