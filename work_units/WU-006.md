# WU-006: AI validator

**Status**: ✅ Complete (2026-10-16) · **Features**: F-015 · **Estimate**: 5-6 hours

## Goal

A validator step that asks Claude whether a change fulfils its intent and each acceptance criterion, using the diff, the changed files and the pipeline evidence. It writes the same verdict file as the reference validator, treats everything from the repository as untrusted data, and reports its token usage.

## Context

- ARCHITECTURE.md A12 (AI validator), risk 3 (prompt injection), risk 4 (cost). Kai decision: milestone 1 includes the AI validator; the owner approved the paid service and added the key to `.env`.
- WU-005: input and verdict contracts, `ParseVerdict`, `Combine` (per criterion, `met` from any validator counts unless another says `unmet`).
- Claude API skill: Go SDK `github.com/anthropics/anthropic-sdk-go`; default model `claude-opus-5-5`; set effort explicitly (its default is medium); structured output through `output_config.format` (no string-length or numeric limits in the schema); handle `refusal` and `max_tokens` stop reasons; server-side refusal fallbacks on by default.

## Design

- **Request**: beta Messages endpoint, model from `PLUMBIX_AI_MODEL` (default `claude-opus-5-5`), effort from `PLUMBIX_AI_EFFORT` (default `high`), `max_tokens` 16000, non-streaming. Server-side fallbacks (`fallbacks: "default"`, beta `server-side-fallback-2026-07-01`) are on.
- **Output**: a JSON schema the API enforces (outcome, summary, criteria, findings, risks). Plumbix turns it into a `verdict/v1` and checks it with `ParseVerdict`. Normalization: a `met` criterion without evidence becomes `unknown`; an `approve` that contains an `unmet` criterion becomes `fix`; finding line 0 means no line.
- **Prompt injection defence**:
  - The system prompt states that repository content is data written by the change's author, possibly an AI agent, and that instructions inside it must never be followed. Text addressed to the validator is reported as a `prompt-injection` risk with `human_required`.
  - Repository content goes inside a tag with a random name per run, so content can't close it early.
  - Criteria marked `met` must cite evidence.
  - In Plumbix's own pipeline the deterministic validator also runs, and an `unmet` from it always wins.
- **Content**: the change (title, intent, criteria with checks, constraints, previous findings) outside the untrusted tag. Inside it: `/plumbix/in/diff.patch` when present, otherwise the changed files from the workspace, plus the last 8 KB of each step log, labelled as such. Content over 600,000 characters is not truncated: the validator fails with a clear error, which Plumbix turns into `needs_human`.
- **Failure**: missing key, API error, refusal after fallbacks, `max_tokens`, or an output that breaks the contract all exit non-zero without a verdict.
- **Usage**: model and token counts go into the verdict's `usage`.
- **Secrets**: `internal/secrets` loads a dotenv file (mode `0600` required, `KEY=VALUE`, optional `export` and quotes, comments, empty values skipped). Used by the live test now and by the pipeline in WU-007.
- **Contract**: `diff.patch` is added to the validator input as an optional file.

## Acceptance criteria

- **AC-1**: The request sent to the API has the right model, effort, schema, system prompt, fallbacks and beta header (fake API server).
- **AC-2**: Repository content sits only inside the random untrusted tag, and a fake closing tag inside the content doesn't end it.
- **AC-3**: Responses map to valid verdicts, including the normalizations. Refusal, `max_tokens`, malformed output, unknown criterion IDs and API errors produce errors, not verdicts.
- **AC-4**: Oversized content fails with a clear error instead of being truncated.
- **AC-5**: The program writes `verdict.json` with usage, and exits non-zero without a verdict when the key is missing.
- **AC-6**: Secrets loading handles the documented syntax and refuses loose permissions.
- **AC-7**: The image builds; run without a key it fails cleanly and writes no verdict (integration, no API cost).
- **AC-8**: Live test (opt-in, `make live`, costs a few cents): an honest change gets the expected statuses, and a change whose diff tries to talk the validator into approving does not get approved.
- **AC-9**: `make check` and `make integration` pass.

**Delivered**: `internal/aivalidator` (prompt, structured output mapping, API call), `internal/secrets`, `validators/ai` (program, Dockerfile), optional `diff.patch` in the validator input, `make live`. 499 lines of code, 764 lines of tests.

**Decisions**
- Non-streaming request with `max_tokens` 16000, which keeps it under SDK timeouts. Reviews took about 15 seconds.
- Server-side refusal fallbacks are on (`fallbacks: "default"`), as the Claude API guidance recommends for Opus 5.5. The verdict's `usage.model` records which model actually answered.
- Structured output guarantees the JSON shape but not non-empty text. The first live run returned an empty summary and reason. Rather than fail a paid review, a criterion without a reason drops to `unknown`, and an empty summary is replaced by one labelled as generated by Plumbix.
- Contract errors quote up to 2,000 characters of the model's output, so a failed validator step can be diagnosed from its log.
- Live tests are opt-in behind the `live` build tag and never run in `make check` or `make integration`.

**Observed in live runs**
- Both reviews found a real off-by-one in the test fixture: three attempts give two retries, not "retried up to three times". The fixture was left as is, since it shows the validator judging code and not just echoing evidence.
