# WU-023: External validator step and `plumbix review --watch`

**Status**: ✅ Complete (2026-10-18) · **Features**: F-003, F-004 · **Estimate**: 2 sessions · **Kai**: 2DAEKX

## Goal

A validator step can be satisfied by a reviewer outside the pipeline: Plumbix publishes a review brief and waits for a verdict posted back. A Claude Code session, or `plumbix review --watch` on any machine with Claude Code installed, pulls the next brief, reviews with its own tools and authentication, and posts the verdict. People use the Claude they already have, and the server stays the author of the prompt and the gate on the verdict (A26).

## Context

- A12 and Q07: AI lives in validator steps, never in the core. The external step keeps that: the core publishes a prompt and checks a verdict; the model call happens wherever the reviewer runs.
- Claude Code cannot be called back by an MCP server (no sampling support), so the direction is pull: the reviewer asks Plumbix for work.
- A verdict that never arrives, or does not pass the checks every verdict passes, is a validator error: the change goes to a person, never to approval.

## Design

**Pipeline.** A validator step with `external: true` has no `image`, `run`, `env` or `secrets`; `timeout` bounds the wait (default 1 hour). Example: `- {name: ai-review, validator: true, external: true, needs: [build, test], timeout: 2h}`.

**Run.** When the scheduler reaches an external step, the engine builds the review brief from the same inputs a container validator gets: the AI validator's prompt (system and user parts, repository content in the untrusted block), the verdict JSON schema with the change's criterion ids, head, base, iteration, repository URL, and the operator's tool policy and model. It stores a `reviews` row (status `pending`, an expiry at the step's timeout, the brief), emits `review.requested`, writes a line to the step log, and waits. When a verdict arrives the engine writes it as the step's `verdict.json` and the step succeeds; the usual verdict reading and checks follow. At the timeout the review is `expired` and the step is `timed_out`, a validator error.

**Claiming.** `GET /api/v1/reviews/next?reviewer=<name>&repo_id=<id>&wait=<seconds>` long-polls up to the wait (at most 55 s) and atomically claims the oldest pending review the reviewer may take, emitting `review.claimed`. A reviewer never receives a change it submitted itself (`submitted_by` equals the reviewer name; the MCP server of WU-024 tightens this to session identity). The claim mints a one-time token, kept as a SHA-256 hash, and returns the brief with it; 204 when nothing is pending. `POST /api/v1/reviews/{id}/verdict` `{token, verdict}` accepts the verdict once: the review must be claimed and not expired and the token must be the one minted for the claim (409 otherwise), and the verdict must pass the same checks as a file from a container (400 with the problems). An unclaimed review cannot be answered.

**Settings.** `ai_tools`: `read-only` (default) or `full`. It travels in the brief as `tools`; `plumbix review` and the later container image obey it. The web Settings page shows it as a toggle.

**CLI.** `plumbix review --watch [--repo <id>] [--reviewer <name>] [--once] [--model <m>] [--tools read-only|full]`: long-polls `next`, checks the head out in a worktree under `<data_dir>/review/<repo>` with the user's own git access, runs `claude -p` with the brief's system prompt, user prompt and schema (`--output-format json --json-schema`, `--restricted` unless tools are full, `--no-session-persistence`, a turn and budget cap), posts the verdict, prints one line per review, and keeps going.

**Events and contracts.** `review.requested` `{run_id, step, review_id, expires_at}` and `review.claimed` `{review_id, reviewer}`; OpenAPI paths and the `ReviewBrief` schema; `external` in `pipeline.schema.json`.
