# WU-020: Pipeline editor

**Status**: ✅ Complete (2026-10-17) · **Features**: F-002, F-004 · **Estimate**: 10 hours (two sessions)

## Goal

Edit a repository's `.plumbix/pipeline.yaml` in the browser and propose the result as a change. Design: `web/design/PIPELINE.md`, layout 2a ("Stages, top-down"), prototype `web/design/design/Pipeline.dc.html`. Save never writes to the protected branch: it pushes a branch and opens a normal change, validated with the pipeline on the target branch (policy source, ARCHITECTURE 4.2), so a change cannot weaken its own checks. The new pipeline applies when that change merges, and because it edits `.plumbix/` it always ends in `needs_human`: a person approves every pipeline change (A9).

## Context

- WU-019 gave the format every field the design uses. The mapping from the design's placeholder keys to format v1: step `id` is `name`; `run[]` is `run` (a list when more than one command, a string for one); `evidence` is `artifacts`; an env row with the secret toggle on is a name in `secrets` (the value is the secret's name, never shown or stored here); `needs`, `timeout`, `retries`, `allow_failure`, `when.paths` and `stages` are as named.
- Validators run after their needs finish. The editor writes a validator's `needs` as every non-validator step, which is what "validators always run last" means in the format; the inspector hides needs for validators.
- A14: new endpoints go on the protected mux. A15: a branch that already exists on the host is refused, not overwritten. A20: the push uses the repository's own token when set; a refused push is `push_denied` (today's merge rule) with the Settings hint.

## Design

**API.**
- `GET /api/v1/repos/{id}/pipeline[?branch=]` → `{file, branch, sha, content, pipeline, problems, last_run}`. `branch` defaults to the first protected branch (or `main`). `pipeline` is the parsed model (steps with `name`, `image`, `commands`, `needs`, `env`, `secrets`, `artifacts`, `timeout`, `validator`, `retries`, `allow_failure`, `paths`, `stage`; and `stages`); `problems` lists parse errors (path, line, message) when the file does not parse, in which case `pipeline` is null; `last_run` is the newest finished run on that branch with `{run_id, head, steps: {name: {status, duration_ms}}}` so cards can show last durations. A missing file is `content: ""` with one problem.
- Live validation while editing is not needed: the YAML view is read-only and the model cannot express an unparsable file; the existing `POST /api/v1/pipelines/check` stays for other clients.
- `POST /api/v1/repos/{id}/pipeline/changes` `{branch, title, intent, content, target_branch?}` → 201 `Change`. The server parses the content (400 problems when invalid), fetches, reads the target head, commits the one file on it as Plumbix with the title as message, pushes the new branch (409 `branch_exists` if the host has it; 409 `push_denied` if refused), then submits the change with two text criteria: "The pipeline file parses and the step graph has no cycles" and "Every step image can be pulled", and the intent as given. Pushes never force.

**Engine and git.** `gitops.Mirror.CommitFile(parent, path, content, message)` builds a tree from the parent with one blob replaced through a temporary index and commits it with Plumbix as author and committer; `PushBranch(branch, sha)` pushes without force and refuses when the branch exists. `Engine.PipelineFile(repoID, branch)` and `Engine.ProposeFile(repoID, Proposal)` wrap them with the fetch lock and host credentials. The newest finished run comes from the existing `ListRepoRuns`.

**Web.** New screen `/pipelines` and `/pipelines/{repoId}`; sidebar item "Pipelines" with the repository count. Rows: header (title, repository segmented control with a `•` for unsaved edits, `file at branch · sha`, Visual / YAML), toolbar (`+ Step`, `Add after`, `Add in parallel`, `Merge into one step`, `Group as stage`, `Remove`, hint), canvas with stage bands (named stages, then unnamed waves by needs depth, validators last; cards 360×60 on a grid of at least three columns; same-stage needs as lines in an SVG under the cards, cross-stage needs as `after x` chips), the floating frosted inspector while something is selected, and the edit bar (edit count and summary, Discard, Save as change with branch, title, intent and the auto criteria; after the push a `role="status"` row with Open change). The YAML view is read-only with `+` marks on lines not in the original. Unsaved edits live in memory per repository (lost on reload, as the design implies). `vm/pipeline.ts` holds the model, `fromApi`, `toYaml`, the operations (add, add after, add in parallel, rename with needs rewrite, remove with rewire, validator toggle, merge, group, needs without cycles), `layoutBand`, `diffSummary`; `pages/PipelinesPage.tsx` renders it.

## Completion

**Delivered**: `gitops.CommitFile` and `PushBranch` with `ErrBranchExists`; `Engine.PipelineFile` and `Engine.ProposeFile`; `GET /api/v1/repos/{id}/pipeline` (parsed model, problems, last-run durations) and `POST /api/v1/repos/{id}/pipeline/changes` (400 problems, 404, 409 `branch_exists` and `push_denied`, 201 change with validation started), OpenAPI schemas `PipelineFile`, `PipelineModel`, `PipelineStep`, `PipelineLastRun`, `PipelineProposal`; the web model `vm/pipeline.ts` (`fromApi`, `toYaml`, `yamlDiff`, `diffSummary`, `saveDefaults`, operations, `layoutBand`, `bands`) and the `/pipelines` screen with the Pipelines sidebar item; fake-server endpoints for tests. ARCHITECTURE 4.2 paragraph and A22, CONSTRAINTS, PROJECT, CONTEXT_LOG.

**Evidence**: `make check` green (Go, 96 web tests across 14 files, lint, build); `make integration` green. Test-first: `TestCommitFileReplacesOneBlobOnTheParent`, `TestPushBranchCreatesAndNeverOverwrites`, `TestPipelineFileReadsTheBranchHead`, `TestProposeFilePushesANewBranchOnly`, `TestRepoPipelineEndpoint`, `TestProposePipelineOpensAChange`, 12 view-model tests, 8 page tests.

**Decisions made here**: the browser builds the YAML and the server parses it before committing (the format's parser is the single judge); validators the editor writes need every plain step; a string `run` for one command, a list for more; secret env rows map to the `secrets` list under the secret's own name; unsaved edits live in memory per repository; chips that do not fit whole collapse into `+N` with a title.

**Self-use**: the editor's path was used once on Plumbix's own pipeline (change `c_ksdqhdpa5ib3`, branch `pipeline/stage-checks`): the four parallel steps grouped as stage `checks`; every step and both validators passed and the change stopped at `needs_human`, as rule 5 requires for a `.plumbix/` edit. That exposed a gap: a person has no approve action, so no pipeline change can merge through Plumbix until one exists (open decision, raised 2026-10-17). The review also noted that the editor writes the model, not the text, so comments in the file are lost.

**Deferred**: keeping comments and the author's key order when a file is saved (the editor serialises the model); a human approval action; stage rows in run evidence (the run view still lists steps flat); a live `plumbix pipeline check` while typing (the YAML view is read-only, so the editor cannot produce an unparsable file); dark-theme tuning of the band hues once the pill colours settle.
