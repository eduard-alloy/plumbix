# WU-066: Criteria sets

**Status**: ✅ Complete (2026-10-30) · **Features**: F-001, F-010, F-011 · **Kai**: X6Q5JY (workstream F8QK66, milestone M2 PZTRDV) · **Decision**: A43 · **After**: WU-063

## Goal

Acceptance criteria belong with the specification, written before the code by the person who owns the intent. WU-062's form puts them in the pull request body, where the author of the code writes and can edit them. A criteria set is a first-class object in Plumbix that a specification tool (Kai first) creates when the spec is settled; a change only names it.

## Design

- **Object**: `POST /api/v1/criteria-sets` with `task` (free text or a reference such as a Kai task), `owner`, `criteria[]` (the `CriterionInput` shape, checks included) returns `cs_<id>`; `GET /criteria-sets` and `GET /criteria-sets/{id}`; `PUT` edits a set no change has used and is refused afterwards (`criteria_set_used`). Written only through the API token or a browser session, so a pull request can never create one. `plumbix criteria add|list|show`.
- **Reference**: `criteria_set` on `ChangeInput`, or one line `Acceptance criteria: cs_<id>` in a pull request body. At intake Plumbix copies the set's criteria onto the change, frozen, and records `criteria_set: {id, owner, task}` on the change and in `change.submitted`. A pull request that names a set and also lists items gets the set, and the gate check says the body's list was ignored. A missing or unknown id leaves the change with the body's criteria (or the submission's) and a note.
- **Kai side** (Kai's own unit): when a task's spec is settled, Kai posts its acceptance criteria as a set and keeps the id with the task, so the pull request or submission can name it.
- **Later, not here**: a URL form for other sources, frozen the same way, with an allowlist of hosts; a Settings rule that a repository requires a set.
- **Rejected** (A43): Plumbix fetching from Kai; editing a set in place after use.

## Completion

Done 2026-10-30. As built: `POST/GET/PUT /api/v1/criteria-sets` with `CriteriaSetInput {task, title, owner, source, criteria}`, steps only; `used_by` on a set; `criteria_set_used` on a `PUT` after use, checked in the same transaction as the write; `criteria_set` on `ChangeInput` and on the MCP `submit_change` tool, `acceptance_criteria` then optional; the body line in a pull request; `Change.criteria_set {id, owner, task, problem}` and `change.submitted.criteria_set`; the gate check and the change page say where the criteria came from. The API test's fixture is the body Kai's `plan publish X6Q5JY --dry-run` produced, so the two sides agree on the wire. Submitted through Plumbix's own gate. Left: the owner forms differ between Kai (`user@full.host`) and Plumbix's CLI default (`user@shorthost`); both are "the person as the surface knew them".

## Fixes

**Iteration 1** (`approved`; ten findings taken, two of them major): a set is frozen inside the change's own transaction (`freezeCriteriaSet`), and only at the version its criteria were read at, so an edit landing between the read and the write is a conflict rather than a change recorded under criteria the set no longer holds; the freeze is a flag on the set that no later edit of the change clears, so a pull request dropping its reference leaves the set frozen; a set's steps are checked against the head's pipeline like a body item's; the MCP tool's forwarding of `criteria_set` and the `change.submitted` payload against the schema are tested; the model comment sits on its field; this file no longer says the change landed before it did.

**Iteration 2** (`approved`; five minor findings taken): a set edited between the read and the write is `ErrCriteriaSetChanged` (`criteria_set_changed` on the API), no longer dressed as the open-branch conflict; one `change.CopyCriteria` serves the API and the pull-request paths, the steps cloned in both; the stacked model comment is one.

**Live check** (after the deploy): `kai plan plumbix publish X6Q5JY` was refused with `title: must be at most 200 characters`, since Kai sends the task's full title and a set's title was bounded like a change's. A set's title is the specification's own, so it is bounded like a criterion's text (2000) instead; OpenAPI says so. The `freezeCriteriaSet` comment names the error it returns.
