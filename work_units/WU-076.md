# WU-076: examples/first-run, from nothing to an approved verdict

**Status**: ✅ Complete (2026-11-06) · **Features**: docs · **Estimate**: one session · **Kai**: C4W3V7 (workstream XVACVT, milestone O2 00A866) · **Follows**: WU-074 · **Source**: outside feedback of 2026-11-06, point 3; A48

## Goal

A new user on a clean Mac with Docker runs one script and gets an approved verdict and a merge in under ten minutes, without opening ARCHITECTURE.md, and the example cannot rot because an integration test runs it.

## What is wrong today

- No `examples/` directory. The quickstart shows the files inline, but a reader still types them.
- The minimal pipeline, the change and a criteria set exist nowhere as files a reader can copy.

## Design

1. **`examples/first-run/`**: `repo/` is the sample repository as it is on `main` (one function `Balance`, no test, and the smallest useful `.plumbix/pipeline.yaml`: a `test` step and the reference validator); `_change/ledger_test.go` is the change, under an underscore so Go tools at the root ignore it (`repo/` has its own `go.mod`, so `./...` skips it as a nested module); `criteria.json` is a criteria set, posted before the change exists, both criteria bound to the `test` step; `change.json` is the submission naming the set; `README.md` explains the files.
2. **`first-run.sh`** starts a Plumbix server of its own (port 6410, data under `$TMPDIR/plumbix-first-run`) so nothing the user already runs is touched; builds `plumbix-reference-validator:dev` through `POST /api/v1/images/{name}/build` from the sources embedded in the server when the image is missing; creates the bare repository and the working copy, commits `main`, registers, posts the criteria set, pushes the branch, submits with the set id, polls `change show` until the state settles, prints the verdict, merges, shows `main`, and leaves the server running with a `plumbix login` link. `--stop` stops it, for the test. The binary comes from `PLUMBIX_BIN`, `plumbix` on `PATH`, or `bin/plumbix`; WU-075 will make the first of those a download.
3. **`first_run_test.go`**, build tag `integration`, skips without Docker, builds the binary from the tree, runs the script with `--stop` on port 6412 under `t.TempDir()`, and asserts `verdict: approved`, `state: merged` and `first run complete` in the output. `make integration` runs it with the other Docker-backed tests.
4. The README's quickstart gets one sentence pointing at the script.

## Completion

Test first: `first_run_test.go` was written and run before the script existed (it failed to compile on the Docker client's newer `Ping` signature, then failed on the missing script); green once the script was written: the run on this machine built the binary, started the server on 6412, found the validator image present, and reached `verdict: approved`, `state: merged` and `first run complete in 10 s`, 11.7 s for the test. `go vet ./...`, `go build ./...` and `gofmt` are clean with the example in the tree: `repo/` is a nested module and `_change/` an ignored directory, so neither is compiled at the root, and the test file is behind the `integration` tag.

The image-build path: the script was run keeping its server on 6413, and `POST /api/v1/images/plumbix-reference-validator/build` on that server built the image from the embedded sources and reported `succeeded` after 6 s (layers cached; a clean machine pays the `golang` and `alpine` pulls once). The script's own branch for a missing image uses that call and polls the build until it leaves `running`.

Timing on this machine: 9 to 10 s end to end with images present. A clean Mac adds the image pulls (`golang:1.27` is the large one) and the reference validator build, well inside ten minutes on an ordinary connection; that bound is the script's to print, not a measurement from a clean machine, which no machine here is.

Iteration 1 came back fix-requested with two real bugs and they were fixed in iteration 2: a second run over a server the first had left on the port deleted that server's data and then talked to it (now a previous run's server, known by its pid under the directory, is stopped first; anything else on the port is an error); the image-build poll had no bound (five minutes now). Also from that review: the server is stopped on any failure, not only with `--stop`; the explanation of a non-approved verdict prints even under `set -e`; the rerun and the image-build path are each a test now (`TestFirstRunCanRunAgainOverItsOwnServer`, `TestFirstRunBuildsTheValidatorImage`, the latter through `PLUMBIX_EXAMPLE_BUILD_IMAGE=yes`); three tests pass in 47 s. AC-2 names `examples/first-run.sh`; the script lives at `examples/first-run/first-run.sh`, the same thing one directory down.

Iteration 2: the counting reviewer could not assess AC-2 (no clean-machine timing exists) and asked a person to run the script cold or accept the estimate; the owner decides. From its findings, iteration 3 stops a previous server only when its pid is still a `plumbix serve`; iteration 4 tightens that to the server's own data directory on the command line (`ps -p <pid> -o command=`), so a reused pid, another server of the user's, or a renamed binary is never killed. Iteration 5 adds `-ww` to that `ps`, since macOS can cut a long command line. Held each time on AC-2's clean-machine timing, which only a person can measure or accept; accepted carry-overs: ids are read from JSON with grep and sed (the tests guard the format), and the integration test runs under `make integration`, not in the merge pipeline, like every Docker-backed test of this repository.

Closed by the owner's decision A49: a wall-clock bound on a visitor's machine is never a criterion, since nothing in the pipeline can measure it and the project cannot fix what it would fail on; AC-2 is read as "the script runs unattended to a merge and prints its own time", which the integration test proves.
