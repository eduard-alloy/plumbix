# WU-010: Merge on approval, bypass detection and alerts

**Status**: ✅ Complete (2026-10-16) · **Features**: F-001, F-007 · **Estimate**: 7-8 hours

## Goal

A human merges an approved change and Plumbix lands exactly the validated code on the target branch, on any host. The poller notices commits that reached a protected branch without a verdict and raises an alert. Token expiry warnings become alerts too, so the web interface can show them.

## Context

- ARCHITECTURE.md 5.4 (merge), 5.5 (bypass detection), A10 (squash by default), 4.1 (`POST /changes/{id}/merge`, `GET /alerts`).
- WU-007 engine and `gitops`, WU-008 poller and host credentials, WU-009 both hosts behind the boundary.
- CONSTRAINTS: neither host can enforce merges in v1 because the PAT acts as the user, so Plumbix flags bypass commits instead (Q13).

## Design

**What may merge.** The change must be `approved`, and its latest run is the approved one. After a fresh fetch, two checks against that run:
1. The source branch still points at the validated commit (`run.head`). Otherwise `source_moved`: new commits were pushed and must be validated first.
2. The target branch points at the run's base (`run.base`), which means the source already contains the target and the target has not moved since. Otherwise `target_moved`: the validated tree is not what would land. The client brings the target into the source branch, pushes, and Plumbix revalidates.

This is stricter than "the target did not move": it guarantees that the tree landing on the target is byte for byte the tree the validators judged. No merge is ever computed by Plumbix, so there are never merge conflicts to resolve.

**Strategies** (per repo, `merge_strategy`), all built in the bare mirror with `git commit-tree`, no worktree:
- `squash`: one commit with the validated tree, parent the old target head, author the source head's author, committer Plumbix. Message: title, blank line, intent, trailers `Plumbix-Change` and `Plumbix-Run`.
- `merge`: a merge commit with parents old target head and source head, same tree, same trailers.
- `rebase`: the target fast-forwards to the source head. The commits land as they are, since they already sit on top of the target.

**Push.** `git push <remote> <new>:refs/heads/<target> --force-with-lease=refs/heads/<target>:<old>`. If the remote moved between fetch and push, git refuses, nothing is forced, and the merge fails with `push_rejected`. After a successful push the mirror's ref is updated.

**Record.** Table `merges` (change, run, repo, branch, commit, previous, strategy, merged_at). The change exposes it as `merge` in its JSON and moves to `merged`. While a merge is in progress the engine refuses to start a validation for that change, so a push cannot slip in a new run mid-merge.

**Bypass detection.** When a protected branch moves, the poller lists the first-parent commits between the old and new head (only the tip for a branch it has never seen). Commits covered by a Plumbix merge record (`previous..commit`) are Plumbix's own. Any other commit is a bypass: one alert per push, kind `bypass_commit`, naming the branch and each commit's sha, author, time and subject. A Plumbix merge landing on the target starts no plain run: its tree was validated already.

**Alerts.** Table `alerts` (id, kind, key, repo, message, details JSON, created_at, resolved_at). One open alert per kind and key: raising it again is a no-op. Kinds: `bypass_commit` (key `branch@sha`), `token_expiry` (key host kind; raised when the token expires within 7 days or the check fails, resolved by itself once the check passes). `GET /api/v1/alerts?include_resolved=true` lists newest first; `POST /api/v1/alerts/{id}/resolve` closes one.

**API and CLI.** `POST /api/v1/changes/{id}/merge` returns the merged change (200), 409 with `invalid_state`, `source_moved`, `target_moved` or `push_rejected`. CLI: `plumbix change merge <id>`, `plumbix alert list [--all]`, `plumbix alert resolve <id>`.

## Acceptance criteria

- **AC-1**: `gitops` builds squash and merge commits and fast-forwards, pushes with an expected old head, and a push whose expectation is stale is refused without changing the remote.
- **AC-2**: Through the engine, an approved change merges with each strategy; the remote target holds the validated tree, the commit carries the trailers, the change is `merged` with its merge record.
- **AC-3**: Merge is refused when the change is not approved, when the source moved, when the target moved, and when the remote moved between fetch and push; in each case the remote is untouched and the change stays `approved`. A validation cannot start during a merge.
- **AC-4**: The poller raises a `bypass_commit` alert naming the commit and author for a foreign commit on a protected branch, raises none for a Plumbix merge, and starts no plain run for one. Raising the same alert twice keeps one open alert.
- **AC-5**: A token expiring within 7 days raises a `token_expiry` alert; a later healthy check resolves it.
- **AC-6**: Merge and alert endpoints match the OpenAPI schemas; the CLI drives merge and alerts end to end.
- **AC-7**: `make check` and `make integration` pass.

**Decisions**
- A15: merge only when the source contains the target; the validated tree lands unchanged. See ARCHITECTURE.md and Kai.
- Committer identity `Plumbix <plumbix@localhost>`, author copied from the source head. Hosts show the commit as unverified; signing is a later feature.
- A close that races a merge is accepted: the engine logs it and the merge record stands. A dedicated `merging` state was rejected as not worth a new public state.
- Bypass alerts cap the listed commits at 50 and keep the total count.

**Known flake**: with `go test ./...` the AI and reference validator image tests build their images at the same time from the same context. One run failed `TestImageFailsCleanlyWithoutKey` after 21 seconds and passed alone in 1.3 seconds. Not investigated here; recorded in CONSTRAINTS.
