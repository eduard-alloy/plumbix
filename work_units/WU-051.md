# WU-051: Pipeline guard

**Status**: ✅ Complete (2026-10-19) · **Features**: F-002, F-014 · **Estimate**: one session · **Kai**: 6HAQF9 (workstream TCVR9R, milestone I1) · **Decision**: A38

## Goal

A38 gave secrets only to runs on protected branches. Two gaps remained (ARCHITECTURE risk 7): a direct push to a protected branch that edits a pipeline still gets secrets, and a validator step that a change's own pipeline adds still receives its reviewer profile's key. And a person approving a change to `.plumbix/` sees only the diff, not what it does with secrets. This unit adds a check Plumbix runs itself on such changes, and ties secrets on protected branches to pipeline files a person approved.

## Design

- **Guard.** `internal/guard` compares each pipeline file a change adds, edits or deletes (`.plumbix/pipeline.yaml`, `.plumbix/pipelines/*.yaml`) at the merge base and the head, and returns risks, each `human_required`, from validator `pipeline-guard`, area `pipelines`:
  - a summary per file: added, changed or deleted; its triggers; the secrets its steps name, new ones marked; images new to the file; steps added or removed; steps whose commands, env, or needs, caches and conditions changed;
  - flags: a secret not set in the secrets store (a typo, or a name chosen to look like another); a triggered pipeline that names secrets and also runs on branches that are not protected (those runs get none); a step whose commands both name a secret it receives and use a network tool (curl, wget, nc, ssh, scp, http or https URLs); a file that does not parse.
  No repository file defines or can remove the guard. Its risks join the run's result; such a change already ends in needs_human (`.plumbix/` rule), and the guard's risks say what the person is approving.
- **Approved pipeline files.** A table `approved_pipelines` (repository, path, SHA-256 of the content, change, time). When a change merges, the content of every pipeline file the merge changed is recorded as approved by that change. Files the merge did not touch are not recorded, so a file pushed past Plumbix is never approved by an unrelated merge.
- **Secrets on protected branches.** A run on a protected branch gets secrets only when its pipeline file's content is approved; otherwise a step naming one errors with "the pipeline file at this commit is not a version a person approved; bring it in through a Plumbix change". A withheld protected run raises a `pipeline_unapproved` alert that resolves when an approved version runs. Trust on first use: a repository with no approved files at all approves every pipeline file at the protected head at once, at the first protected run or, when a merge comes first, as the target stood before that merge (logged), so existing setups keep working.
- **Validator keys.** In a change's run, a validator gets its reviewer profile's key only when the target branch's pipeline defines it identically: image, commands, env, secrets, reviewer, external flag, effort and advisory. A validator the change adds or redefines runs without the key and, for AI validators, produces no verdict.

## Acceptance criteria

| # | Criterion | Check |
|---|---|---|
| AC-1 | The guard reports added, changed and deleted pipeline files with triggers, secrets (new marked), new images and step changes, and flags unknown secrets, secrets in pipelines that run off protected branches, secret-plus-network commands and files that do not parse. | guard tests |
| AC-2 | A change that touches pipeline files carries the guard's risks in its result and needs a person; other changes carry none. | engine test |
| AC-3 | A merge records approvals for the pipeline files it changed and no others. | engine and store tests |
| AC-4 | On a protected branch, a run of an unapproved pipeline file gets no secrets and says why; an approved one gets them; a repository with no approvals trusts its first file once. | engine tests |
| AC-5 | A validator the change adds or redefines gets no reviewer key; one matching the target's gets it. | engine test |
| AC-6 | `make check` passes; ARCHITECTURE, CONSTRAINTS, PROJECT and CONTEXT_LOG describe it. | |

## Steps

1. Guard package: tests, then `Review`.
2. Store: migration, approve and lookup, tests.
3. Engine: guard in change runs, approvals at merge, secrets gate, validator keys; tests first.
4. Docs.

## Completion

**Delivered**: `internal/guard` (`Review`, `IsPipelineFile`, `Digest`, the `Store` interface); migration 0016 and `ApprovePipelines`, `PipelineApproved`, `HasPipelineApprovals` in the store; in the engine, `guardReview` in `prepare` with its risks added after `Combine`, `approveMerged` after a merge's record, `gate` deciding secrets for branch, triggered and change runs, and the validator key check in `setupValidator`.

**Evidence**: guard tests (added triggered file with every flag, changed and deleted files, unparsable and unchanged files, path rules); `TestApprovedPipelines` (store); engine `TestGuardReviewsPipelineChanges`, `TestMergeApprovesTheChangedPipelineFiles`, `TestProtectedRunsNeedApprovedPipelineFiles` (first use trusted, an edit pushed past Plumbix withheld, then approved), `TestValidatorsAddedByTheChangeGetNoKey`. Each failed before the code. `make check` green.

**Trade-offs**: trust on first use for a repository with no approvals; the network flag is a pattern match, a hint for the person, not a proof. Secret grants per pipeline stay planned (Kai ZCVFJV).

## Fixes
- 2026-10-19, iteration 1 (fix_requested): a redefined validator kept its key because only name, image, reviewer and external were compared; `sameValidator` now compares everything that decides what runs (commands, env, secrets, effort, advisory too), tested with a changed `run`. Trust on first use recorded only the file being run, so other pipeline files never got secrets, and a merge as the first event trusted nothing; `trustFirstUse` now approves every pipeline file at the protected head, from runs and from merges (target before the merge), tested both ways. Withheld protected runs and failed approval records now raise a `pipeline_unapproved` alert (contracts, Alerts page), which resolves when an approved version runs.
- 2026-10-19, iteration 2 (needs_human for the trust-on-first-use trade-off, the owner's to accept): the guard now names steps whose env, or needs, caches and conditions changed instead of a generic line; the Design section describes the final checks.
- 2026-10-19, iteration 3 (needs_human for trust on first use and the network flag's limits, the owner's to accept): the guard also names steps whose effort or advisory flag changed; the unrecorded-approval alert carries a fixed message, the cause stays in the server log.
