# WU-036: The pipeline editor keeps the file's text

**Status**: ✅ Complete (2026-10-18) · **Features**: F-004 · **Estimate**: 1 session · **Kai**: HCHJ5R · **Decision**: A34

## Goal

Every save from the pipeline editor rewrote the whole file: the header comment that states the A12 rule vanished twice, run lines were requoted, `30m` became `30m0s`, and both reviewers flagged a one-word change as doing more than it said. The owner cannot control what the editor writes, so the editor must write only what changed. After this unit a save applies the edited model as targeted edits on the served file's text: an unchanged model saves byte-identical, comments and the author's formatting survive, and the YAML view shows the text that will be committed.

## Design

**Text, not model.** `web/src/vm/yamlEdit.ts` parses `PipelineFile.content` with the `yaml` package into a document that keeps comments, key order, scalar style and flow or block collections, and applies the model to it: steps are matched by the name they had in the served file (`PStep.src`, kept through a rename), kept in the editor's order (plain steps, then validators); on a matched step each editor-owned key is compared with what the writer would emit and replaced in place only when different, missing keys are appended in the writer's order, editor-owned keys no longer wanted are deleted, and keys the editor does not know are left alone; a new step is appended as a block map with flow lists; `stages` is updated the same way or removed when empty. The document is printed with no line folding and no padding inside flow lists. The old writer, `toYaml`, stays as the fallback when there is no file or the library cannot parse it, and both build a step's keys from one function so they cannot drift.

**One source for the preview.** `renderYaml(model, original)` gives the text the server receives; the YAML view and the push both use it, and the added-line marks come from the base model rendered the same way.

## Completion

**Delivered**: the `yaml` dependency (2.9.1); `desired()`, `stageLists()` and `STEP_KEYS` in `pipeline.ts` shared by `toYaml` and the new writer, `PStep.src`, `renderYaml`, `yamlDiff` over rendered text; `web/src/vm/yamlEdit.ts` (`applyModel`: steps matched by served name, keys compared and replaced in place, owned keys deleted, unknown keys kept, new steps and stages appended, list style kept, fallback to `toYaml`); the page pushes and previews the rendered text, the YAML view's foot says so; ARCHITECTURE (A22 note, A34), CONSTRAINTS, README, PROJECT, CONTEXT_LOG.

**Evidence**: `yamlEdit.test.ts` against Plumbix's own pipeline file: byte-identical when unchanged; `effort: medium` on ai-grok is exactly one added line with the header, the quoting and `30m` intact; a changed scalar is replaced in place, a dropped flag deleted, a renamed step keeps its trailing comment, an unknown key survives; a new step and stage are appended in the writer's order and block lists stay block; turning a step into a validator edits in place; unreadable text falls back to the writer; the YAML view marks only the added line. The page tests and the model tests pass unchanged apart from the foot text. `make check` green.

**Decisions made here** (A34): text over model; the library in the browser so the preview is the commit; the old writer as fallback only.

**Deferred**: a comment above the first step stays with the list when steps are reordered (the library attaches it to the collection); env key order changes replace the whole `env` map; the server could refuse a proposal whose text parses to something other than what the editor meant (a cross-check of the parsed model against the proposal) as a belt beside these braces.
