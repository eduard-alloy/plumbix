# WU-013: API token

**Status**: ✅ Complete (2026-10-16) · **Features**: F-008 (first part) · **Estimate**: 2-3 hours
**Order**: runs after WU-003 and before WU-004. Work unit IDs are stable identifiers; PROJECT.md lists the execution order.

## Goal

Every API call except the health check requires a token that only the machine's owner can read. Step containers can reach the port on Docker Desktop, but they can't read the token, so they get 401 and never data.

## Context

- Kai decision "Protect the API with an automatically generated local token (option A)", 2026-10-16.
- WU-003 finding: on Docker Desktop, containers reach the host's loopback through `host.docker.internal`, `gateway.docker.internal` and `192.168.65.254`.
- The server still binds only to loopback. This adds a second layer, it does not replace the first.

## Design

- **Token file**: `<data_dir>/api-token`, 32 random bytes from the operating system's secure random source, written as 64 hex characters. Created on first `plumbix serve` with mode `0600`, using exclusive create so two servers can't race.
- **Data directory**: created with mode `0700` if missing.
- **Permission check**: the server refuses to start if the token file is readable or writable by group or others, or if its content isn't 64 hex characters. The error says how to fix it.
- **Auth**: every route under `/api/v1/` except `GET /api/v1/health` requires `Authorization: Bearer <token>`. Comparison is constant-time. Failures return 401 with `WWW-Authenticate: Bearer` and the shared error shape, code `unauthorized`. The response never says whether a token was missing or wrong.
- **Clients**: an exported helper reads the token from the data directory, for the CLI commands that come in WU-004.
- **Rotation**: delete the file and restart the server. Documented in the README.
- **Browser**: the one-time login link and session cookie come with the web interface in WU-011, together with Host and Origin checks, since cookies are where cross-site request forgery and DNS rebinding matter.

## Acceptance criteria

- **AC-1**: The first `serve` creates the data directory (`0700`) and the token file (`0600`, 64 hex characters). Later starts reuse the same token.
- **AC-2**: The server refuses to start when the token file has looser permissions or malformed content, with an error explaining the fix.
- **AC-3**: `POST /api/v1/pipelines/check` without a token, or with a wrong one, returns 401 with `WWW-Authenticate: Bearer` and code `unauthorized`. With the right token, it works as before.
- **AC-4**: `GET /api/v1/health` works without a token.
- **AC-5**: Integration: a step container probing the real API through every route Docker offers gets 401 or no connection, never a successful response.
- **AC-6**: `make check` and `make integration` pass. The OpenAPI file declares bearer auth.

## Steps (test first for each)

1. Token file: create, reuse, permission and format checks.
2. Auth middleware: missing, wrong and right tokens, health exemption, constant-time compare.
3. Wire into `serve`: data directory, token file, middleware. End-to-end test through `runServe`.
4. Replace the network-only security test with one that probes the real API from a container.
5. OpenAPI, README, docs.

**Decisions**
- Unknown routes also need the token, so callers without it learn nothing about which endpoints exist.
- An empty server token rejects every request instead of accepting an empty header.
- The token file is created with exclusive create, so two servers starting together can't overwrite each other's token.
- A trailing newline in the token file is accepted, so editing it by hand doesn't break it.
