# WU-068: A review the platform closes says so, with a reason

**Status**: ✅ Complete (2026-11-04) · **Features**: F-010 · **Estimate**: short · **Kai**: SQ7K52 (workstream F8QK66, milestone M3 AE14T5) · **Follows**: WU-067 · **Source**: Chart-AI's second-day follow-up, ask 6 (A45)

## Goal

On 2026-11-04, on the second Mac's instance (change c_rvqclaspi4le, run run_d5yks5prnus5, review rv_qj2qyc7earfh), a server restart ended a run whose external review was claimed. The loop's progress lines and verdict were then refused with 409 ("review X is expired, or the token is not the one handed out with its brief"), and the stream's last word about the review was `review.claimed`. A reader could not tell a review the platform dropped from one the loop abandoned. The claim token survives a restart (its hash is on the review row); the status is what changes.

## Design

Four ways a claimed review ends without a verdict (code at 2913fd3):

1. The step's timeout passes (`waitExternal`, deadline) → `timed_out`.
2. The run is cancelled: a newer iteration superseded it, or its change was closed → `run_cancelled`; the server stopped (`Engine.Shutdown`, cause `errShutdown`) → `server_stopped`. Both reach the same `ctx.Done` path; `context.Cause` tells them apart.
3. Crash recovery (`Engine.Recover` on a run left running) → `server_restart`.
4. The reviewer never fetched the brief (`Engine.ReleaseReview`) → the review is pending again; `review.released` now says `reason: reviewer_gone`.

- **Event** `review.expired` `{review_id, reviewer?, reason}`, emitted inside `Store.ExpireReview` and `ExpireRunReviews` through the write transaction, the reason passed in by the engine; `reviewer` is absent for a review nobody had claimed. `review.released` keeps its meaning (pending again, the next claim takes it) and gains `reason`.
- **Record**: the reason persists on the review row (`expired_reason`, migration 0023) and reads back on `Review.ExpiredReason`; the 409 a late verdict or log line gets names it ("review X is expired (server_stopped), or the token…"); the step log's last line names it.
- **Contract wording** (OpenAPI `validateChange`, events schema `run.finished`): after a restart Plumbix never starts an iteration itself; a run that ended because the server stopped ("interrupted because the Plumbix server stopped" on a graceful stop, "interrupted: the Plumbix server stopped during this run" after a crash recovery) leaves the change at `needs_human` as a hold a person or a client releases with `POST /changes/{id}/validate`.
- **Not in this unit**: resuming a claimed review across a restart (the step's container context is gone); re-opening the loop's claim.

## Steps

1. Failing store tests: an expiry carries the reason on the row and in `review.expired`; a release says `reviewer_gone`; the lifecycle test emits the new type.
2. Failing engine tests: each of the four endings emits one `review.expired` with its reason and the log line names it; the 409 names it.
3. Reason constants, the event type and payloads, the schema entry, migration 0023, the store's transactional expiry, the engine's cause mapping.
4. Contract wording; README, ARCHITECTURE, CONSTRAINTS, PROJECT, CONTEXT_LOG; `make check`.
