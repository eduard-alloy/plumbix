# WU-019: Pipeline format: stages, retries, allow_failure, path conditions

**Status**: ✅ Complete (2026-10-17) · **Features**: F-002, F-003 · **Estimate**: 6 hours

## Goal

The pipeline editor design (handoff 2, layout 2a, `web/design/PIPELINE.md`) relies on fields format v1 does not have. Decided 2026-10-17: the format grows first, then WU-020 builds the editor with every field. Everything added is optional, so every existing pipeline file parses and runs exactly as before.

## Context

- Format v1 (WU-002): `version`, `steps[]` with `name`, `image`, `run`, `needs`, `env`, `secrets`, `artifacts`, `timeout`, `validator`. Unknown fields are errors. Schema in `contracts/pipeline.schema.json`, kept in step with the parser by `TestSchemaAndParserAgree`.
- Scheduler (WU-003): steps start when every need succeeded; a failed need skips dependents; validators run after every need finished.
- Step outcomes reach validators as `evidence/<step>/status.json` (`validator-input.schema.json` `$defs/stepStatus`); the reference validator's `check.steps` needs `succeeded`.
- The design's keys (`needs`, `when.paths`, `allow_failure`, `retries`, `stages`, `evidence`, `{ secret: name }`) were placeholders. `evidence` stays `artifacts`; secrets stay the `secrets` list; the others are added as named here.

## Design

**Format additions (version stays 1).**

| Field | Meaning |
|---|---|
| `steps[].run` | A string as before, or a list of strings. A list runs as one script with `set -e`, one command per line, so the step stops at the first failure. |
| `steps[].retries` | 0 to 5. A step that fails or times out is run again, up to this many more times. Only the last attempt's outcome counts. Not for errored steps (the runner could not start them). |
| `steps[].allow_failure` | A failed or timed-out step does not fail the run and does not skip the steps that need it. Its status stays `failed` or `timed_out`; the run records that the failure was allowed. Not allowed on validators. |
| `steps[].when.paths` | Globs (`*`, `**`, `?`) over workspace paths. For a change's run the step runs only if a changed file matches one of them; otherwise it is `skipped` with reason `paths` and counts as satisfied for the steps that need it. For a plain branch run there is nothing to compare, so the step runs. Not allowed on validators. |
| `stages` | Top-level mapping of stage name to step names. Display grouping only: each step is in at most one stage, validators cannot be in a stage. Steps and runs carry the stage name. |

**Scheduler.** `StepResult` gains `Attempts`, `Allowed` (the failure was allowed), `Reason` (`needs` or `paths` for skipped steps). `Options` gains `ChangedFiles []string` and `ChangesKnown bool`. A need is satisfied when it succeeded, failed with `allow_failure`, or was skipped by its paths. Retries re-run the same job; the log gets a one-line separator per attempt.

**Records and contracts.** `run.Step` gains `attempts`, `allowed_failure`, `reason`, `stage` (all omitted when zero); migration 0008 adds the columns. The `step.finished` event payload and `status.json` gain `attempts`, `allowed_failure` and `reason` (not `stage`: a validator judges steps, not their grouping). The reference validator counts a step skipped by its paths as met for `check.steps` ("did not need to run"); an allowed failure is still unmet when a criterion names that step.

**Web.** The step rows say `allowed` after a tolerated failure, `paths unchanged` after a path skip, and `attempt N` when a step was retried. No new screens; the editor is WU-020.

**Not changed.** Plumbix's own `.plumbix/pipeline.yaml`. Policy source (target branch's validators) and the needs_human rule for `.plumbix/` edits.

**Decisions made here**: an allowed failure keeps status `failed` (the run and the UI say what happened; only the consequence changes); a step skipped by its paths is met for a criterion that names it, a step skipped by a failed need is not; a trailing `**` does not match the directory itself; retries never re-run an errored step because the runner, not the code, failed; validators may retry but may not be conditional or allowed to fail.
