# WU-018: Settings: tokens, AI guidance and model

**Status**: ✅ Complete (2026-10-16) · **Features**: F-004, F-005, F-015 · **Estimate**: 7 hours

## Goal

Everything an operator has to configure after install happens in the browser: git host tokens and other secrets, review guidance for validators, and the AI model. Secrets never leave the server once set. Opened by WU-012, whose merge waited on a token that was only settable by editing a file.

## Context

- A13 (secrets in a dotenv file, 0600), A18 (server-owned file, write-only from the browser, reloaded live), A19 (guidance plus model, no effort knob, no full prompt).
- Q07: the core holds no AI; guidance is "operator instructions to validators", not an AI feature. Only the model knob names the AI validator, and only as an environment variable it already reads.
- The settings page is not in the design handoff; it follows the design system.

## Design

**Secrets, live.** `secrets.Manager` owns the configured secrets file: it loads it, rewrites it atomically with mode 0600 on `Set` and `Unset` (replacing or removing the key's line, keeping every other line), and keeps the current values in memory. Values are validated (a key is `[A-Za-z_][A-Za-z0-9_]*`, a value has no newline) and quoted when they need it. The engine and the poller read secrets and host adapters through the manager on every use (`host.Source`), so a token set in the browser is used by the next fetch, push and token check with no restart.

**Settings store.** Migration 7 adds `settings(key, value, updated_at)`. `settings.Service` keeps `ai.model`, `guidance.global`, `guidance.repo.<id>` and, for each secret key, `secret.<KEY>` = when it was last set. It also knows the well-known secret keys and their purpose.

**Guidance to validators.** `validation.Input` gains `guidance: {global, repository}` (both optional strings; the contract and its test are updated). The engine fills it from the settings for every validator step. The AI validator renders it under "Operator guidance" before the untrusted block, marked as instructions from the Plumbix operator; the reference validator ignores it. The model setting is injected into validator steps as `PLUMBIX_AI_MODEL` unless the step's own `env` sets it (`scheduler.StepSetup.Env`, step env wins).

**API.**
- `GET /api/v1/settings` → `{ai_model, guidance, secrets: [{key, set, known, purpose, updated_at?}]}`. Known keys always appear; keys present in the file appear too.
- `PUT /api/v1/settings` `{ai_model?, guidance?}` → the same shape. Empty string clears.
- `PUT /api/v1/settings/secrets/{key}` `{value}` → 204. `DELETE` → 204. Values are never logged or returned.
- `POST /api/v1/settings/secrets/{key}/check` for host tokens → `{ok, expires_at?, message}` by calling the adapter's token check now.
- `GET` and `PUT /api/v1/repos/{id}/settings` → `{guidance}`.

**Web.** `/settings`: Git hosts (GitHub token; Azure DevOps token and expiry date), AI review (Anthropic key, model, global guidance), Other secrets (any key a pipeline step names). Each secret row shows set or not set and the last change, with Set (reveals an input, saved on Enter or Save), Remove and, for host tokens, Check with its result inline. The repositories page gets a Guidance control per row that opens an inline textarea. A Settings item joins the sidebar.

**Not in scope.** Editing the AI effort or prompt; secrets in the CLI (the file still works by hand); per-repo model.

## Acceptance criteria

- **AC-1**: `secrets.Manager` sets, replaces and removes keys in the file, keeps other lines and comments, writes 0600, refuses bad keys and multi-line values, and `Load` reads back exactly what was set.
- **AC-2**: After a token is set through the API, the next `ListHeads`, `Fetch` and push use it and the token check runs with it, in the same server process. The value never appears in any response or log.
- **AC-3**: Guidance set globally and per repository reaches `change.json` for validator steps; the AI validator's prompt carries it outside the untrusted block; the model setting reaches validator steps as `PLUMBIX_AI_MODEL` unless the step sets its own.
- **AC-4**: Settings endpoints match their OpenAPI schemas; the settings page and the repository guidance control work against the fake server in the web tests.
- **AC-5**: `make check` and `make integration` pass.

**Decisions**
- Any key is accepted as a secret, not only the known ones, because pipeline steps name their own secrets. Known keys always show, custom ones show while set.
- "Last changed" is only known for secrets set through Plumbix; a key set by hand shows as set with no time.
- The token check reuses the host adapter's expiry check: for GitHub it calls the API, for Azure DevOps it reads the expiry date secret, so a wrong Azure token is only found by the next fetch.
- The settings page is not in the design handoff; it uses the design system's tokens and components and will get the same visual pass as the rest.
