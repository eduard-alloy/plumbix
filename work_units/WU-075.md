# WU-075: Tagged releases with prebuilt binaries

**Status**: ✅ Complete (2026-11-06) · **Features**: F-004 · **Estimate**: one session · **Kai**: RQPMV9 (workstream XVACVT, milestone O2 00A866) · **Follows**: WU-076 · **Source**: outside feedback of 2026-11-06, point 4; A48

## Goal

A visitor installs Plumbix by downloading one file: a tagged release carries binaries for macOS and Linux on arm64 and amd64 with a checksums file, built by a workflow that runs on a tag and nowhere else, and the shipped validator images built from such a binary carry the release version.

## What is wrong today

- No tags and no releases; building needs Go 1.27, Node 20 and npm. The README's install section starts with `git clone` and `make build images`.
- The web interface is already embedded (`embed.go` carries the validator build context too), so a single binary is self-contained; the SQLite driver is pure Go (`modernc.org/sqlite`), so cross-compiling needs no C toolchain.
- Images the server builds already carry `org.plumbix.version` equal to the server's version (WU-032); images built by `make images` carry no label.

## Design

1. **`make release`** builds the web interface once, then `CGO_ENABLED=0` binaries for `darwin/arm64`, `darwin/amd64`, `linux/arm64`, `linux/amd64` into `dist/` as `plumbix-<os>-<arch>` with `-X main.version=$(VERSION)`, and writes `dist/checksums.txt` (SHA-256). `VERSION` defaults to `git describe`, so a tag builds as its name.
2. **`.github/workflows/release.yml`** runs on a pushed tag `v*` only: checkout, Go from `go.mod`, Node 20, `make release VERSION=<tag>`, then `gh release create <tag> dist/* --verify-tag --generate-notes`. Permissions: `contents: write`. No other trigger; nothing on push to a branch.
3. **`make images`** labels the local images with `org.plumbix.version=$(VERSION)` so they match what the server builds; the server's own build path is unchanged and already keys the label to its version, which a release binary carries. The Images page's version check (WU-032) therefore compares against the tag.
4. **README**: the install section leads with the download (`curl -LO` of the release asset, `chmod +x`, onto `PATH`), keeps the source build below it, and tells a download user to build the two shipped images from the Images page or let `first-run.sh` do it. `PROJECT.md` says `0.1.0` and the status line says the first tagged release exists.
5. **The tag** `v0.1.0` is pushed on the merge commit of this change, after the merge, since a tag-triggered workflow runs from the tagged commit's own workflow file. The release is checked with `gh release view`, and this file's completion records it in the next change.

## Acceptance criteria

## Steps

1. `make release` red (no rule), then the target; green: four binaries that print the version, a checksums file.
2. The workflow; its YAML parses; `make images` labels.
3. README, PROJECT; CONTEXT_LOG, roadmap; submit through Plumbix.
4. After the merge: tag `v0.1.0`, push it, watch the run, check the release; record it; Kai `RQPMV9` done.
