# WU-035: Containerised Claude Code validator image

**Status**: ✅ Complete (2026-10-18) · **Features**: F-003, F-004 · **Estimate**: 1 session · **Kai**: HZ3AB5 · **Decision**: A33

## Goal

Claude Code judges changes today only through `plumbix review --watch` on a machine where someone is signed in. A server with no loop running has only the API validators, and the owner wants Claude Code's review with tools on an unattended server, beside Grok in the same run. After this unit Plumbix ships a third image, `plumbix-claude-code-validator`, that runs `claude -p` inside the pipeline on a long-lived token the person mints with `claude setup-token` (or an API key), built from the Images page like the other two.

## Design

**One runner.** `internal/claudecode` holds what `internal/reviewer` did by hand: the `claude -p --output-format stream-json` invocation with the system prompt file, JSON schema, tool policy (`--restricted` with `Read`, `Grep`, `Glob` under read-only; `Bash` added under full, never `Edit`), bounded turns and budget, the stream reader that turns tool uses into progress lines (`turn 3: Read internal/engine/external.go`) and the result object with its usage and model. The loop calls it; so does the new validator. Behaviour of the loop is unchanged, its tests still pass.

**The validator.** `validators/claude-code` is a pipeline validator like `validators/ai`: it reads `/plumbix/in`, builds the prompt with `review.BuildPrompt` and the schema with `review.OutputSchema`, runs the shared runner in `/workspace` (mounted read-only by the engine), checks the structured output with `review.ToVerdict` and writes `/plumbix/out/verdict.json`. Environment: `PLUMBIX_AI_MODEL` (empty means the CLI's default), `PLUMBIX_AI_TOOLS` (`read-only`, the default, or `full`), `PLUMBIX_AI_MAX_TURNS` (default 40), `PLUMBIX_AI_API_KEY` with the token or key, `PLUMBIX_CLAUDE` for the executable (tests). A value starting with `sk-ant-oat` reaches the CLI as `CLAUDE_CODE_OAUTH_TOKEN`, anything else as `ANTHROPIC_API_KEY`; the value is never printed. Progress lines and the final line (`claude code validator: approve · 12 turns · $0.31 · claude-opus-5-5`) go to stderr, into the step log.

**The image.** `validators/claude-code/Dockerfile`: the Go binary built in the usual stage, then `node:24-bookworm-slim` with `git` and `@anthropic-ai/claude-code` pinned, a non-root user with a writable home (Claude Code writes under it), `DISABLE_AUTOUPDATER=1`, no login baked in. It joins `images.ShippedImages`, so the Images page lists and builds it.

**The profile kind.** `claude-code-image` is a fourth reviewer kind in the api family: it binds to container validator steps like `anthropic` and `openai`, carries tools and a model, has a key secret (the token), refuses a base URL and, for now, an effort. The engine's `profileEnv` passes model, tools and the key for this kind. The settings page offers it with a note on how to mint the token; the editor's reviewer select shows its label.

## Acceptance criteria

| # | Criterion | Check |
|---|---|---|
| AC-1 | The shared runner runs `claude` with the same arguments the loop used and parses the stream (tool uses as progress, result with usage and busiest model); the loop's tests pass unchanged. | claudecode and reviewer tests |
| AC-2 | The validator binary writes a verdict from a fake `claude` run read-only in the workspace with the brief's prompt and schema; a full policy adds Bash; the token reaches the CLI under the right variable by prefix; no key means a clean failure naming the secret and no verdict. | validators/claude-code tests |
| AC-3 | The image is a shipped image; `claude-code-image` profiles validate (no base URL, no effort, a key secret, tools), reach the container as `PLUMBIX_AI_MODEL`, `PLUMBIX_AI_TOOLS` and `PLUMBIX_AI_API_KEY`, and the page and the editor name the kind. | images, settings, engine, api, web tests |
| AC-4 | `make check` passes; the image builds locally and fails cleanly without a token (integration test); ARCHITECTURE, CONSTRAINTS, README, PROJECT, CONTEXT_LOG describe it. | |

## Steps

1. `internal/claudecode` extracted from the loop, with tests; the loop uses it.
2. The validator binary and its tests.
3. The Dockerfile, the shipped image entry, the integration test.
4. The profile kind: settings, engine, OpenAPI, web.
5. Docs; build the image on the owner's server.

**Evidence**: `TestRunPassesPromptSchemaPolicyAndEnvironment`, `TestFullPolicyAddsBashAndBudget`, `TestFailuresAreErrors`, `TestReadStreamAcceptsABareResultAndDrainsTheRest`, `TestDescribeToolRendersPathsRelativeAndCutsLongArguments` (claudecode); the loop's tests unchanged (reviewer); `TestWritesVerdictFromClaudeCode`, `TestTokenToolsAndTurns`, `TestFailsWithoutVerdict` (validators/claude-code), `TestImageFailsCleanlyWithoutKey` under the integration tag; `TestClaudeCodeImageProfilesAreAPIProfilesWithAToken` (settings); `TestProfileEnvByKind` (engine); the images and API list tests with three shipped images; the settings page test for the kind. `make check` green.

**Decisions made here** (A33): one runner for the loop and the image; the kind is in the api family; the token is a named secret mapped by prefix; no effort for this kind.

**Deferred**: a `--effort` for Claude Code once the CLI flag is relied on; a model list in the profile form; the owner mints a token and binds a step (a person's act: `claude setup-token`, the secret under the profile's key secret, the image built on the Images page, a step `image: plumbix-claude-code-validator:dev` with `reviewer: <name>`).
