# WU-032: Images page, the inspect layer

**Status**: ✅ Complete (2026-10-18) · **Features**: F-002, F-004 · **Estimate**: 1 session · **Kai**: YCZ7AK · **Decision**: A32

## Goal

The images a pipeline runs are opaque: the two validators Plumbix ships exist only where someone ran `docker build`, and the owner's AI validator image predated the OpenAI provider until rebuilt by hand, with nothing to say so. After this unit an Images page lists every image the registered pipelines reference with what the server knows about it, and the two shipped images show whether they match the server and can be rebuilt from the page.

## Design

**Shipped images.** `internal/images` knows the two images Plumbix ships, `plumbix-reference-validator` and `plumbix-ai-validator`, with their Dockerfiles under `validators/`. The build context (`go.mod`, `go.sum`, `internal/`, `validators/`) is embedded in the binary from a root package, so a deployed server can rebuild them without a source checkout. A build tags `<name>:dev` and labels it `org.plumbix.version=<server version>` and `org.plumbix.shipped=<name>`; the page compares the label with the running server's version.

**Inspection.** `GET /api/v1/images` lists, for each image name referenced by any registered repository's pipeline at its default branch plus the shipped two: whether it is present locally, created time, size, digest, the version label when it is a shipped image and whether it matches, and the repositories and steps that use it with the validator flag. Reading pipelines reuses `Engine.PipelineFile`.

**Builds.** `POST /api/v1/images/{name}/build` starts a build of a shipped image (own images come in WU-033) and answers 202 with a build id; builds run one at a time on the server, their output streamed by the Docker API into `<data_dir>/images/builds/<id>.log`; `GET /api/v1/images/builds/{id}` returns status and log, which the page polls. A build is a person's act: the route sits behind the session or token like every other, and the MCP server does not expose it.

**Page.** `Images` in the sidebar: one card per image with name, shipped badge, status line (present with age and size, or missing), the version check for shipped ones, who uses it, and for shipped images a Build button with the streamed log. The lead says what a build is: code run on the server's Docker daemon outside the step sandbox, as trusted as a pipeline edit.

## Completion

**Delivered**: `embed.go` at the module root with the shipped images' build context; `internal/images` (`ShippedImages`, `List` with presence, created, size, digest, version status and users, `Build` of a shipped image through the Docker API with the labelled tag, one at a time, `GetBuild` with the log, `ContextTar`); `runner.Docker.Client()`; API routes `GET /images`, `POST /images/{name}/build`, `GET /images/builds/{id}` with OpenAPI, wired in `serve`; the Images page with the sidebar entry, cards with status and users, Build and the followed log; fake server and tests; ARCHITECTURE (component, API, data layout, A32), CONSTRAINTS, README, PROJECT, CONTEXT_LOG.

**Evidence**: `TestListMergesPipelineUsesAndShippedImagesWithStatus`, `TestBuildSendsTheEmbeddedContextAndKeepsTheLog`, `TestOneBuildAtATime` (images, against a fake Docker that reads the tar); `TestImagesListAndShippedBuild` (api); the three Images page tests. `make check` green.

**Decisions made here** (A32): the build context is embedded rather than fetched; shipped images are told apart by a label, not by name alone; a build is a person's act and not an MCP tool.

**Deferred**: own images with a Dockerfile editor (WU-033); pulling a missing third-party image from the page; pruning old builds' logs.
