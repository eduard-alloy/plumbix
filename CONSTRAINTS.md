# Plumbix Constraints

Newest first. Each entry cites its source in DISCOVERY.md.

## Security
- Secrets reach a step only in runs on a protected branch (A38): `schedulerOptions` withholds them otherwise and a step naming one errors with `secret X withheld: ...`. This covers change runs too, whose source branch is never protected, so validators must take keys from reviewer profiles, not `secrets:`. Pipelines still run on every branch. On a protected branch, secrets also need the pipeline file's content to be approved (`approved_pipelines`, WU-051): only a merge records approvals, and only for the pipeline files it changed; never record approvals for files a merge did not touch, or a push past Plumbix gets laundered. A validator gets its reviewer key only when the target branch defines it identically (`sameValidator`: image, commands, env, secrets, reviewer, external, effort, advisory); compare everything that decides what runs with the key. Trust on first use covers every pipeline file on the protected branch at once (`trustFirstUse`), also when a merge is the first event.
- Secrets set through the API are written to the configured secrets file by `secrets.Manager` (atomic rename, mode 0600, other lines and comments kept) and are never returned, logged or echoed in errors; only set/unset and the time of the last change through Plumbix are shown. Handlers that receive a secret log the key, never the body; the token check redacts the value from any adapter error. The manager re-reads the file when its mtime changes, so hand edits while the server runs are seen on the next use and kept by the next write. (WU-018, A18)
- Browser sign-in (A17): login links and session cookies are stored as SHA-256 hashes only; links live 10 minutes and work once, sessions 30 days. Every cookie request must carry the listen address as `Host`, and state-changing ones an `Origin` of `http://<listen>`; the bearer token is exempt from both. The sign-in exchange is a POST, never a GET, so prefetchers cannot consume a link. (WU-016)
- The web app is served outside `/api/` with a same-origin Content-Security-Policy and no inline scripts; `/api/` keeps its protection. The container probe also checks `GET /api/v1/changes`. (WU-016)
- On Docker Desktop, step containers reach the host's loopback through `host.docker.internal`, `gateway.docker.internal` and `192.168.65.254`. Loopback binding alone never protects the API. (WU-003)
- Every API route except health needs the bearer token from `<data_dir>/api-token`. The server refuses a token file readable by others. New endpoints go on the protected mux by default. Never mount the data directory into a step container. (WU-013, A14)
- `TestStepCannotUseHostAPI` (in `internal/api`) must keep passing: a container probing the real API must never get data back. (WU-013)
- Secrets live in a dotenv file with mode `0600`. The repo's `.env` is git-ignored, and only `.env.example` is committed. (A13)
- The AI validator treats all repo content as untrusted data. In Plumbix's own pipeline an AI approval alone is never enough; the deterministic validator must also approve. (A12, risk 3)
- Plumbix binds only to local addresses and refuses to start otherwise until authentication exists. (Q12)
- Step containers have no network path to the Plumbix API. Validators report verdicts through step output only. (Q12)
- Each git host PAT (GitHub fine-grained, Azure DevOps) is scoped to code read/write, kept in a local secrets file outside the repo, and never logged. (Q13)
- Git gets tokens only through its process environment and the askpass script in the data directory, never through arguments or URLs. `-c credential.helper=` keeps personal credential helpers out. (WU-008)
- Plain shell execution without container isolation is not allowed. Agent-written code is untrusted. (Q04)

## Integration
- Azure DevOps does not report a personal access token's expiry to the token's holder (its token lifecycle API needs a Microsoft Entra ID sign-in). The expiry warning relies on `PLUMBIX_AZURE_DEVOPS_TOKEN_EXPIRES` in the secrets file; without it there is no warning. Azure DevOps ignores the basic-auth user name when the password is a token. (WU-009)
- Plain git remotes (host `git`): absolute paths, `file://`, `ssh://`, scp-style. No credentials; SSH runs in batch mode unless the user set their own SSH command. Local remotes should be bare repositories. (WU-015)
- GitHub and Azure DevOps are the v1 hosts. Both sit behind one narrow host boundary designed from these two real implementations. (Q03, revised)
- Pushes are detected by polling in v1, because a local-only Plumbix is unreachable for service hooks. (Q12)
- Neither host can enforce merges in v1 because the PAT acts as the user. Plumbix flags bypass commits instead. (Q13)

## Architecture
- Import polish (WU-043): repository names are shown through `decodeName` (URL encoding read, invalid encoding kept); the import panel reads `GET /settings` secrets to know whether `PLUMBIX_GITHUB_TOKEN` or `PLUMBIX_AZURE_DEVOPS_TOKEN` is set and forces a per-repository token when not; `gitops` maps git's credential prompt failures ("could not read Username", "terminal prompts disabled") to `ErrNoCredentials`.
- Publish (WU-042, A35): `host.GitHub.CreateRepository` reads the token's login (`GET /user`) and posts to `/user/repos` or `/orgs/{owner}/repos` with `auto_init: false`; `host.AzureDevOps.CreateRepository` posts to `{org}/{project}/_apis/git/repositories?api-version=7.1` with basic auth and treats a 203 sign-in page as a rejected token; both prefer a given token over the host token, and `AuthWith` gives the push the same token. `gitops.Publish` refuses a folder with a remote or without commits, adds `origin`, pushes `--all` and sets the checked-out branch's upstream. It is the one import that changes the local folder. `InspectFolder` accepts only the top of a working tree (WU-041 review).
- Import (WU-041, A35): `api.inRoot` is the only way a typed path reaches git: `~` is the import root (`os.UserHomeDir`, `Deps.ImportRoot`; empty disables the routes), others must be absolute, symlinks are resolved (whole path for inspect, parent for clone) and the result must lie in the root. `gitops.InspectFolder` reads through git only; `gitops.Clone` refuses a destination with files (`ErrNotEmpty`) and passes credentials through askpass. `change.DetectRemote` rewrites GitHub and Azure DevOps SSH remotes to HTTPS (the registered URL), keeps other SSH, scp, file:// and absolute remotes as plain git, and refuses other HTTPS hosts; `web/src/vm/remote.ts` mirrors it for the clone tab. The page registers, stores a token, checks access, then clones, and says what is registered when a later step fails.
- Usage and notes (WU-039): Anthropic and Claude Code report `input_tokens` without cached input, OpenAI-compatible providers include it in `prompt_tokens`; verdicts normalise to uncached `input_tokens` plus `cache_read_tokens` and `cache_write_tokens`. `Engine.appendVerdictNotes` runs only for container validators with a verdict, because `waitExternal` already wrote the notes for external steps.
- Fitted stages (WU-038): `bands(p, sel, width)` fits every band when any band's natural width exceeds `width`; `MIN_CW` 240, `CW` 360, column gap `BGX` 40, fitted row gap `WRAP_GY` 24 (10 otherwise). The page derives the width from the canvas's `clientWidth` minus 58 px of padding and border, minus 352 px while the inspector is open; jsdom reports 0, which keeps the natural layout in tests unless stubbed. Below one `MIN_CW` column the canvas still scrolls.
- External switch (WU-037): `toggleExternal` clears the step's reviewer both ways, since a profile answers one family only (A29), and a validator leaving the loop with no image gets `plumbix-ai-validator:dev`. The inspector filters profiles by `kind === 'claude-code'` against `s.external`.
- Editor writes (WU-036, A34): `web/src/vm/yamlEdit.ts` applies the model to the served file with the `yaml` package (2.9, the web app's only runtime dependency beside React); printed with `lineWidth: 0` and `flowCollectionPadding: false`, which is what makes Plumbix's own file round-trip byte for byte. Steps are matched by `PStep.src` (the served name, kept through a rename) so a rename edits the name scalar in place and keeps the step's comments; a comment above the first step belongs to the list and stays on top when steps are reordered. `desired()` in `pipeline.ts` is the one list of keys a step writes, used by both `toYaml` and the text writer; a key the editor does not own is never touched or removed. Validators' `needs` are always every plain step, so adding or removing a plain step rewrites every validator's `needs` line. Test fixtures whose `content` does not match their `pipeline` (the page fixtures) still work: unmatched steps are appended, and a `steps: []` placeholder turns block.
- Claude Code in the pipeline (WU-035, A33): `internal/claudecode.Run` is the one place that invokes `claude -p` (arguments, tool policy, stream reading, result checks); `internal/reviewer` and `validators/claude-code` both call it, so a change to how Claude Code is driven lands in both. `settings.KindClaudeCodeImage` is an api-family kind: `Family()` stays api, `PutReviewer` refuses `base_url` and `effort` on it and gives it the default key secret; `profileEnv` passes `PLUMBIX_AI_MODEL`, `PLUMBIX_AI_TOOLS` and the key as `PLUMBIX_AI_API_KEY`, never `PLUMBIX_AI_EFFORT`. The validator maps the secret to `CLAUDE_CODE_OAUTH_TOKEN` when it starts with `sk-ant-oat`, else `ANTHROPIC_API_KEY`, and drops `PLUMBIX_AI_API_KEY` from the CLI's environment (`claudecode.Options.Drop`). Under the full tool policy the token is still readable by the commands Claude Code runs, which is inherent to Bash plus a credential; read-only is the default and the page warns. The image is `node:24-bookworm-slim` with `@anthropic-ai/claude-code` pinned (2.1.302), `git`, a non-root user whose `HOME` is writable (the CLI writes state there even with `--no-session-persistence`), `DISABLE_AUTOUPDATER=1`; `images.ShippedImages` has three entries, so tests that index the list use `len(ShippedImages)`. A profile of this kind bound to a `plumbix-ai-validator` step fails cleanly (that binary wants `ANTHROPIC_API_KEY`); the pipeline step must run the Claude Code image.
- Reasoning effort (WU-034): measured on 2026-10-18 against xAI, a 22k-token review request to `grok-4.7` took 399 s with 30,134 hidden reasoning tokens by default and 110 s with 6,927 under `reasoning_effort: low`; tiny requests took 1 to 2 s, so the model's reasoning, not the transport or the schema, is the cost. `settings.Reviewer.Effort` (API kinds; `low`, `medium`, `high`, or empty for the vendor's default; column `effort`, migration 0014) and a validator step's `effort:` (which wins) reach the container as `PLUMBIX_AI_EFFORT`; `aivalidator.Config.EffortSet` says the operator chose, and only then does the OpenAI-compatible path send `reasoning_effort` (`xhigh` and `max` become `high`), retrying once without it when a 400 names the field. `validation.Usage.ReasoningTokens` (`reasoning_tokens` in the verdict contract) comes from `completion_tokens_details.reasoning_tokens` and is printed in the validator's final line and the step's verdict line. A finding's `criterion` in the output schema is now an enum of the change's ids plus the empty string: Grok wrote `intent` into a free string and broke the contract.
- Own images (WU-033, A32): `images.Service.PutOwn` validates the name (`[a-z0-9][a-z0-9._-]{0,62}`, not a shipped name) and the Dockerfile (non-empty, at most 64 KB, a `FROM` line) and writes `<data_dir>/images/own/<name>/Dockerfile`; `Build` resolves a name to a shipped image or an own one, whose context is its directory and whose tag is `<name>:latest`, with labels `org.plumbix.own` and `org.plumbix.dockerfile` (sha256 of the file). References are canonicalised (`canonical`: a bare name gets `:latest`) so a pipeline's `image: lint-tools` and the built `lint-tools:latest` are one entry. Status for own images compares the Dockerfile label with the stored file: `current`, `stale` (edited since the build), `unlabelled`, `missing`. Deleting removes the definition only; Docker keeps the built image until pruned. Routes return problems through `imageHandlers.fail`.
- Images (WU-032, A32): `embed.go` at the module root embeds `go.mod`, `go.sum`, `internal/` and `validators/` (about 1.5 MB, test files included) as the Docker build context of the shipped images; `images.ContextTar` packs it, and `images.Service.Build` sends it with `Dockerfile` set to the image's path and labels `org.plumbix.version=<server version>` and `org.plumbix.shipped=<name>`. Inspection reads the label back: `current` when it equals the server's version, `stale` when not, `unlabelled` when a shipped image was built by hand, `missing` when absent, `present` for third-party images. Builds run one at a time in a goroutine under their own context, with the Docker JSON stream copied into `<data_dir>/images/builds/<id>.log`; `ErrBusy` is 409. The Docker client is shared with the runner (`runner.Docker.Client()`). The API test harness carries a fake Docker (`fakeDockerImages`).
- The container AI validator reports progress on stderr (WU-031): `aivalidator.Config.Progress` receives `asking <model> through the Anthropic API (effort e): N characters of prompt` or `asking <model> at <host> (OpenAI-compatible): N characters of prompt, response_format f`, and `<host> refused response_format f; retrying with g` on a fallback; the binary points it at stderr, which the Docker runner streams into the step log as it happens (`ContainerLogs` with follow), so the log panel moves. Only model, host, sizes and effort are printed; tests check the key never appears. The first Grok run took 154 s for a 6k-token prompt with nothing in the log: the latency was the model's, not the prompt's.
- Advisory validators (WU-030, A31): `pipeline.Step.Advisory` (validators only) flows into `validation.ValidatorResult.Advisory`; `Combine` tags the validator's outcome, assessments, findings and risks with `advisory` and skips them in every rule (`mergeStatus` ignores advisory assessments, an advisory reject or fix moves nothing, an advisory human-required risk or missing verdict calls nobody, and an advisory validator alone is still "no validator ran"); the engine leaves advisory validators out of the target branch's required list. `run.Step.Advisory` is a new `steps` column (migration 0013). The web counts (`N findings · N risks`, blockers) cover counting validators only; a criterion's headline assessment is the first counting one. The editor round-trips `advisory: true` and offers it as a switch on validators.
- Step caches (WU-029, A30): `pipeline.Step.Cache` is parsed by `parser.cache` (absolute, cleaned, not `/`, not `/workspace` or under it, no `..`, no duplicates, `MaxCachePaths` 8, plain steps only). `Engine.setupPlain` mounts `<data_dir>/cache/<repo_id>/<step>/<cacheSlug(path)>` read-write at each path, creating it `0700`; the step is part of the path because steps run in parallel and the first cold run showed `build`, `test` and `lint` corrupting one shared module cache (downloads into one directory from three containers); `cacheSlug` is the path's words joined by dashes plus eight hex characters of its SHA-256, so `/go/pkg/mod` and `/go-pkg/mod` cannot collide. Validators never get a cache (read-only workspace, judge from evidence) and the external step has no container. Caches are per repository by construction; nothing prunes them, and deleting a directory is the reset. The editor model carries `cache`, writes it after `artifacts`, drops it when a step becomes a validator, and unions it when steps merge.
- Reviewer kinds and families (A29): `settings.KindClaudeCode` joins `anthropic` and `openai`; `Reviewer.Family()` is `FamilyExternal` for claude-code and `FamilyAPI` otherwise. `Service.Reviewer(ctx, name, family)` returns family's default for an empty name (settings `reviewers.default` and `reviewers.default_external`); `SetDefaultReviewer(name)` sets the default of the profile's own family and `Defaults()` reads both. `PutReviewer` refuses a key secret or base URL on claude-code and gives it no default key secret. The engine resolves container validators in the api family (never for `st.External`, which `waitExternal` resolves in the external family) and errors on a cross-family binding. `EnsureReviewers` has a second one-time step (marker `reviewers.split`): an installation migrated under A28 gains `claude-code` from the api default's tools (and model when anthropic) as the external default, and an api profile still called `default` is renamed `claude-api` or `openai-api`; the legacy path now creates both profiles at once. The web page hides the key row and secret name on claude-code cards and shows tools only there; the default badge names its family.
- Reviewer profiles (WU-028, A28) live in `reviewer_profiles` (migration 0012) behind `settings.Service.{Reviewers,Reviewer,PutReviewer,DeleteReviewer,DefaultReviewer,SetDefaultReviewer}`; the default's name is the setting `reviewers.default`. `EnsureReviewers` runs at server start exactly once per installation (marker `reviewers.migrated`): the WU-025 `ai.*` settings become a profile `default` (kind from the provider, key secret `ANTHROPIC_API_KEY` or `OPENAI_API_KEY`) and are removed; a fresh install gets the built-in anthropic one; afterwards an emptied list stays empty. A profile's key secret defaults to `PLUMBIX_REVIEWER_<NAME>_KEY` and may name any secret. The engine's `Settings` interface is now `Guidance` and `Reviewer(ctx, name)`; `reviewerProfile` fails a step whose named profile is missing, and `profileEnv` builds the container validator's variables with the key under `ANTHROPIC_API_KEY` or `PLUMBIX_AI_API_KEY` by kind. External steps take tools and model only from an anthropic profile (named, or the default); naming an openai profile on one is an error written to the step log. The pipeline editor view exposes `external` and `reviewer` per step so the Settings page can say which steps a profile judges.
- Running steps and review progress (WU-027): the scheduler's `Options.Started` hook fires when a step goes in progress, the engine records the step as `running` in the run (no exit, no duration) and emits `step.started`; the finished record replaces it, so a run's step list has each step once and a running step lists before the ones not yet reached. Reviewer progress goes through `Engine.AppendReviewLog`: the review must be claimed with the token, the line is folded to one line, `MaxReviewLogLine` 300 characters, `MaxReviewLogLines` 300 per review and `ReviewLogMinInterval` 500 ms (counters in memory per review, dropped when the step stops waiting, `ErrTooManyLines` is 429 `too_many`), appended to the step log with `O_APPEND` beside the engine's own lines. `plumbix review` reads `claude --output-format stream-json --verbose` line by line (`readStream`): each `tool_use` in an assistant message becomes `turn N: <Tool> <what>` with paths relative to the worktree and commands cut at 120 characters, rate-limited client-side at 600 ms; a fake `claude` that prints one JSON object still works. The web log panel follows a running step by refetching every 2 s (`logFollow.every`) and keeps the view at the bottom; the open log target is re-resolved from the store on every render so the panel sees the step end.
- The AI validator's `openai` provider (WU-025, A25) is `aivalidator.validateOpenAI`: `net/http` only, `POST <base>/chat/completions` with system and user messages, no `temperature` (reasoning models reject it), and `response_format` tried as `json_schema`, then `json_object`, then absent when a 400 mentions the format; the user prompt ends with the schema and a one-object instruction; fences are unwrapped; the answer still goes through `review.ToVerdict`. Settings: `ai_provider` (anthropic default, openai) and `ai_base_url` (http(s) with a host, 200 characters), handed to validator steps as `PLUMBIX_AI_PROVIDER` and `PLUMBIX_AI_BASE_URL` beside `PLUMBIX_AI_MODEL`; the key is a step secret (`PLUMBIX_AI_API_KEY`, else `OPENAI_API_KEY`). `make live` also runs the openai path when `OPENAI_API_KEY` is set.
- `plumbix mcp` (WU-024) is one more API client: the official MCP Go SDK (`github.com/modelcontextprotocol/go-sdk`) serves over stdio, stdout is the protocol so the command prints only to stderr, every tool is a thin wrapper that returns the API's JSON or a tool error carrying the API's code (`target_moved: ...`), and the session identity `mcp:<name>:<6 hex>` is both `submitted_by` for its submissions and the reviewer name for its claims, which is how the own-change rule covers it without a server change. `approve_change` is registered only with `--allow-approve` (A23: approval is a person's act; an agent session must not clear `needs_human` on its own), and `wait_for_verdict` defaults to 4 minutes so it fits under MCP clients' tool-call timeouts, answering "call again" when it runs out. `wait_for_verdict` streams `/events?change_id=` from zero and ignores replayed verdicts of earlier iterations, returning on the running iteration's `verdict.issued`, a final state, an errored run, or its timeout (at most 55 minutes). Tested with the SDK's in-memory transports against a fake API.
- Reviewer presence (WU-026, A27) lives in `engine.presence`, in memory only, keyed by reviewer name with the poll's repository filter; `presenceWindow` is two minutes. The `no_reviewer` alert's key is the repository id, raised through the alert store (`alert.Store` is now part of `engine.Store`) and resolved by `noteReviewer` on every poll whose filter covers it. `plumbix review install` writes `~/Library/LaunchAgents/com.plumbix.review.plist` (launchd, `KeepAlive`, `RunAtLoad`, the installer's `PATH` and `HOME`) or `~/.config/systemd/user/plumbix-review.service` (`Restart=always`); the logic is `reviewer.Install/Uninstall/Status` with the home directory and the command runner injectable, tested with a fake `launchctl` and `systemctl`.
- `plumbix review --watch` (WU-023, change 2): the user prompt goes to `claude` on stdin and the system prompt in a file, since a command-line argument has a size limit and briefs can hold 600k characters of repository content; `--bare` is never passed because bare mode reads only `ANTHROPIC_API_KEY` and would defeat subscription use; the reviewer may read, search and (under the full policy) run, never edit, so `--tools` lists `Read,Grep,Glob` (plus `Bash`) and the run is `--restricted` when read-only; a failed or unstructured `claude` result posts nothing, so the step times out and a person sees it; a verdict that lands in the last poll interval before the deadline is still taken by the step. `plumbix review` without `--watch` or `--once` is a usage error. Tests use a fake `claude` on the PATH (`internal/reviewer`). The long poll uses `client.Wait`, bounded by its context, never `Do` with its 30 s request timeout: a poll cut off after the server had claimed left a review nobody could answer (found on the first real run, 2026-10-18). The server releases a claim when the poller has hung up (`review.released`), and the step log follows release and re-claim.
- External validator steps (WU-023, A26): `external: true` is parsed only on validators and excludes `image`, `run`, `env` and `secrets`; the schema expresses the image rule with `allOf` conditionals next to the existing `run` rule. The scheduler hands such a step to `Options.External` under the step's timeout (`DefaultExternalTimeout` one hour) and errors when no hook is set, so an external step never passes by default. The engine builds the brief with `review.BuildPrompt` (the prompt builder and verdict schema moved from `aivalidator` to `internal/review` so the server does not link the Claude SDK), polls the `reviews` row every second, and a result with no status lets the scheduler record `timed_out` or `cancelled`. Tokens are minted at claim and stored as SHA-256; the claim and token are checked before the verdict is parsed, so a wrong token always gets 409, and an unclaimed review cannot be answered. A waiting external step holds no `runner.max_parallel` slot (the scheduler counts container steps separately). `Engine.Recover` expires the open reviews of an interrupted run, so a verdict posted after a restart is refused rather than accepted for nothing. `TestServerBinaryLinksNoModelSDK` (in `cmd/plumbix`) keeps the Claude SDK and `aivalidator` out of the server binary. The rule that nobody reviews their own change compares the self-declared reviewer name with `submitted_by`; WU-024 ties it to session identity. `GET /reviews/next` long-polls at most 55 s per request.
- Update from main (`POST /changes/{id}/refresh`, `plumbix change refresh`) is for branches Plumbix created only: `Change.plumbix_branch` is set by the editor's propose endpoint and ignored on `POST /changes` (`ChangeInput` keeps it out of JSON), and the engine also checks that every first-parent commit between the merge base and the head is authored by Plumbix. `gitops.MergeBranches` uses `git merge-tree --write-tree` (git 2.38 or later on the server), refuses an ancestor with `ErrNotContained` and names conflicting paths in `ErrMergeConflict`; the push is `Mirror.Push` under a lease on the old head. A refresh calls `Engine.Validate`, so the change must not be final or running, and a standing approval is cleared with the new run. (WU-022, A24)
- A person's approval (`POST /changes/{id}/approve`, `plumbix change approve --reason`) applies to the latest finished run's head: `beginMerge` accepts a run whose outcome was not approval only when `human_approval.head` equals that run's head, and `SetChangeState` to `running` clears the approval columns, so a push after an approval needs a new one. Only `needs_human` and `escalated` can be approved; the reason is required and at most 1000 characters. (WU-021, A23)
- The pipeline editor never writes a protected branch and never forces a push: `gitops.PushBranch` refuses a branch the remote already has (`branch_exists`), `CommitFile` replaces one blob on the target head with Plumbix as author, and the change it opens edits `.plumbix/`, so it ends in `needs_human` by rule 5. Validators the editor writes need every non-validator step; a validator with no needs would start at once, before the steps it should judge. (WU-020, A22)
- A push never moves a change out of `needs_human`, `escalated` or `rejected` (`State.NeedsPerson`); the poller records the new head and the change exposes it as `source_head`. Only `Validate again` or `Close` move those states. (A21)
- Pipeline steps may not set `PLUMBIX_*` environment variables themselves (the parser reserves them), so the AI model reaches validator steps only through the settings (`scheduler.StepSetup.Env`, filled only for names the step or its secrets did not set) or through a secret of that name. Operator guidance is trusted by validators because it comes from the settings, never from the repository. (WU-018, A19)
- The engine and the poller read secrets and host adapters through `host.Source` / `Config.SecretSource` on every use, never from a copy taken at start. New code that needs a token must do the same. (WU-018)
- `gitops` never runs git in the caller's working directory and never passes on `GIT_DIR`, `GIT_WORK_TREE` and the other repository-location variables: in the mirror once it exists, in a neutral directory before. Found by Plumbix's own first self-hosted run: inside a step container the workspace is a worktree whose git directory is on the host, and `git ls-remote` run from there fails. `TestGitRunsOutsideTheCallersRepository` and `TestInheritedGitVariablesAreDropped` keep it. (WU-012)
- Events are appended by the store inside the transaction of the write they describe. A new store write that changes what a client sees must emit one; services never emit, the engine appends only `step.finished`. `TestLifecycleEmitsEvents` keeps `events.Types` and `contracts/events.schema.json` the same set and checks every emitted event against the schema. (WU-014, A16)
- `Hub.Publish` never blocks a writer: a subscriber more than `events.SubscriberBuffer` events behind is cut off and replays from the store. The stream handler subscribes before replaying and skips ids already sent, so clients see no gap and no duplicate. Open streams end only when the hub closes, so the server closes it when its context ends. Events are never pruned in v1. (WU-014)
- A change merges only when the source branch still points at the validated commit and the target branch equals the run's base (the source contains the target). The target then receives the validated tree unchanged; Plumbix never computes a merge. (WU-010, A15)
- Bypass detection walks first-parent commits between the last known head and the new head; commits inside a recorded Plumbix merge range are not bypasses. One alert per push, one open alert per kind and key. (WU-010)
- During a merge the engine refuses to start a validation for that change; a close that races a merge leaves the change closed with a merge record, which is logged. (WU-010)
- Validator steps run after their needs finish, whatever the outcome. Normal steps still need their needs to succeed. (WU-007)
- An errored normal step makes the outcome `needs_human`, never `fix_requested`. (WU-007)
- Only a change's active run may move its state, and cancellation is checked before errors: a cancelled run's errors are not infrastructure failures. (WU-007)
- Timing tests assert ordering or overlap, never wall-clock totals, because the full suite runs packages in parallel. (WU-008)
- Tests never reach the network: git URLs are redirected to local repositories with `GIT_CONFIG_COUNT`/`url.<path>.insteadOf`. (WU-007)
- One process in v1. The scheduler calls the runner only through its interface, so runners can move out later. (ARCHITECTURE A1)
- Required validators come from the target branch's pipeline file. Any change touching `.plumbix/` needs a human. (A9)
- A validator crash or invalid verdict is never approval. Criteria without a check are `unknown` and send the change to a human. (A11)
- Merges are refused if the target branch moved since validation. (5.4)
- Contract files in `contracts/` are the source of truth. Contract tests must check real server output against them. (A7)
- Runtime requirements: system `git` and a Docker-compatible engine. (A3, A4)
- Plumbix never depends on Kai or TRACE. Clients depend on Plumbix's public contracts. (Q06)
- Plumbix's own changes go through the public API, never internal shortcuts. (Q11)
- The core contains no AI and holds no model API keys. Validators are pluggable pipeline steps. (Q07)
- Plumbix does not host git repositories and does not run authoring or fixing agents. (Q02, Q07)
- Server and runner stay separable so runners can move to other machines later. (Q04)

## Formats
- Validator usage on the run result (WU-053): `ValidatorOutcome.usage` is the verdict's `usage` copied as reported, `omitempty`, advisory validators included. Plumbix never computes, converts, estimates or defaults any of it; `cost_usd` is the reviewer's own estimate and a missing value means unknown cost, never zero. The OpenAPI `Usage` schema must stay field-for-field equal to `verdict.schema.json`'s `usage` (`TestRunCarriesValidatorUsage` checks the run against it). `events.schema.json` carries no usage: consumers fetch the run on `verdict.issued`, so the stream stays small.
- A re-check (WU-048) can only tell the import's content from a person's by the `written` hashes the import stamps; content without them counts as a person's and is never replaced. Hash parsed content, never text: re-encoding the YAML would otherwise turn every file into an edit. A person's edit to a step is kept even when its source job changes; the note repeats on every re-check until the person updates the step or removes its `written`. Steps are matched by name, so a job renamed at the source is a removed step and an added one. `git update-index --force-remove` needs a work tree; remove an index entry in a bare mirror with `--index-info` and mode 0.
- Azure templates are inlined at import time (WU-047), so the imported file is a snapshot: a template that changes later is caught only by re-check (WU-048), through the expanded job's hash. Compile-time expressions that need run-time facts, such as predefined variables, `dependencies` and `counter`, are not evaluated; their construct stays disabled with reason `template`. A whole-value expression is spliced, and an embedded one becomes text. Booleans render as `True` and `False`, as in Azure. In a list, an `${{ else }}` may be its own item, so the if chain carries across items. Templates from other repositories resolve only to repositories registered in Plumbix, never by fetching an arbitrary URL from the pipeline file. Stage names are made unique like step names, because one stage template used twice would otherwise produce a file that does not parse.
- Importers (WU-046) must produce files that `ParseTriggered` accepts: `importer.Preview` checks every one and reports a failure as a problem, never writes it. Test fixtures are made-up pipelines; never commit a real project's pipeline files or names. An Azure job maps to one step, so tools installed by one Azure step stay available to the next; mapping each Azure step to a Plumbix step would lose that. `$(name)` is rewritten only for inline variables and the workspace paths; other dotless `$(...)` is left for the shell, as Azure leaves undefined macros, unless a variable group may define it. Templates are not detected as pipelines.
- Triggered pipelines live one per file in `.plumbix/pipelines/<name>.yaml` (WU-045) and parse with `ParseTriggered`; `.plumbix/pipeline.yaml` stays the change pipeline and parses with `Parse`, which refuses `on`. Contract-test files for triggered pipelines are named `triggered-*.yaml`. Every moved head reaches `RunPushed`, including Plumbix merges, which the plain branch run skips. The editor's last-run durations must ignore runs with a `pipeline`. The pipeline-level reasons (`PipelineReasons`) are the step reasons plus `trigger`, kept equal to the schema by a test.
- A disabled step disables its pipeline (WU-044): `readPipeline` refuses it before anything runs, for changes and branch runs alike. The reason codes live in three places, `pipeline.Reasons`, `contracts/pipeline.schema.json` and the OpenAPI `PipelineStep`, and tests keep them equal; the web's `REASONS` labels follow the schema's order. The editor owns `disabled` and writes no `image` for a disabled step that has none, because an empty image would be a parse error. A person can only switch on steps disabled with reason `user`.
- Format v1 additions are optional and additive (WU-019): `run` as a list becomes `set -e` plus one command per line; `retries` re-runs only failed or timed-out steps (never errored ones) and reports the last attempt; `allow_failure` keeps the status `failed` or `timed_out` and marks it allowed (`Result.Succeeded()` stays false; `Acceptable()` also accepts allowed failures and path skips; the engine judges a change by its validators and consults neither); `when.paths` applies only when the changed files are known (a change's run), a trailing `**` names what is under a directory and not the directory itself; `stages` is display only. Step records, `step.finished` events and `status.json` carry `attempts`, `allowed_failure` and `reason` (`needs` or `paths`); step records also carry `stage`. All are omitted when zero. The reference validator counts a step skipped by its paths as met for `check.steps`.
- AI validator output is checked with `ParseVerdict` after conservative normalization: `met` needs evidence, a criterion without a reason is `unknown`, `approve` with an `unmet` becomes `fix`. Repository content never leaves the random untrusted block, and content over 600,000 characters fails instead of being truncated. (WU-006)
- `make live` calls the paid Claude API (about $0.04 per review). It is opt-in and never part of `make check` or `make integration`. (WU-006)
- `contracts/verdict.schema.json` and `contracts/validator-input.schema.json` are checked against Go by contract tests over example files. Rules needing the change's criteria (IDs exist, appear once) are Go-only and listed in the schema description. (WU-005)
- Validator containers run as non-root: Plumbix must make `/plumbix/out` writable and the inputs and workspace readable by any user. (WU-005)
- `.dockerignore` must keep `.env`, `.env.*`, `.git` and `bin` out of every build context. A test enforces it. (WU-005)
- API list endpoints return an object wrapping the array, never a bare array. Field problems use `details.problems: [{field, message}]` and list every problem at once. (WU-004)
- `contracts/openapi.yaml` is checked by `TestResponsesMatchOpenAPI`. Every new endpoint adds its responses to that test. (WU-004)
- The `change` package owns the model and the `Store` interface. Storage code implements it and never holds business rules. (WU-004)
- The pipeline parser and `contracts/pipeline.schema.json` must agree. Every format change adds example files under `internal/pipeline/testdata/` so the contract test covers it. Rules that span fields live in the parser and are listed in the schema's description. (WU-002)
- Invalid input to a check-style endpoint is a 200 result with `valid: false`, not an HTTP error. (WU-002)
- The pipeline format is Plumbix's own minimal, strict YAML with a published, versioned schema. No compatibility with other CI formats. (Q08)

## Development environment
- The web tests run with a 15 s per-test timeout: Plumbix validates itself with six containers at once and a loaded host made a 5 s wait time out. (WU-019)
- Web tests run with Vitest, jsdom and Testing Library against a fake `fetch` and `EventSource` (`web/src/test/server.ts`) and API-shaped fixtures. Fake only `Date` (`vi.useFakeTimers({ toFake: ['Date'] })`): faking timers hangs Testing Library's `waitFor`. A StatePill's screen-reader label is part of its parent's accessible name, so queries by name use unanchored patterns. Page tests call `cleanup()` before `vi.unstubAllGlobals()`: hooks run in reverse order, so without it a load that finishes after the test mounts the stream against the real `EventSource`. Tests that emit events first `await streamOpen()`. (WU-011, WU-017)
- The log panel has no Follow mode: the API lists a run's steps only once they finish, so a log can only be opened for a finished step. Follow arrives with running steps in the API. (WU-017)
- The engine records each step on its run as it finishes (`RecordStep`); `FinishRun` replaces the list. Clients may show a run's steps before it ends but never know which step is running. (WU-011)
- `make build` runs `make web` first, which needs Node and npm; `web/dist` is embedded by `web/embed.go`, so a Go-only build still works and serves a "not built" page at `/`. Vite builds with `emptyOutDir` off so `web/dist/.gitkeep` stays. The Vite dev server is not wired to the API: the cookie checks refuse its Host and Origin, so develop against the built app or add a proxy with `changeOrigin` later. (WU-016)
- `make integration` builds the two validator images concurrently from the same context. `TestImageFailsCleanlyWithoutKey` failed once under that load and passes alone; rerun before suspecting a change. (WU-010)
- The Claude Code sandbox blocks local port binding, Go module downloads (TLS through its proxy fails) and the Docker socket. Tests that bind ports, `go get`/`go mod tidy`, and Docker integration tests run outside the sandbox, or with `sandbox.network.allowLocalBinding: true`. (WU-001)
- Once Go's build cache has been written outside the sandbox, the sandbox can't read it. Run all Go commands outside the sandbox. (WU-002)
- `make check` (build, test, vet, gofmt) is the gate for every work unit. (WU-001)
- `make integration` runs Docker-backed tests (build tag `integration`). macOS ships GNU make 3.81, which ignores `.SHELLFLAGS`. Recipes that pipe must use `set -o pipefail` inline. (WU-003)
- Integration tests that check for leftover containers must filter by their own `plumbix.job` label, because packages run in parallel. (WU-003)
- Tests that start an in-process server must call `http.DefaultClient.CloseIdleConnections()` before stopping it. Otherwise a spare connection from Go's shared transport can hold `Shutdown` for 5 seconds. (WU-004)
